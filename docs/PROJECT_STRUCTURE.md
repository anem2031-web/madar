# هيكل مشروع مدار ومسؤوليات ملفاته

## حالة التصميم وحدوده

هذا هو التصميم التنظيمي الأول للمهمة M2-07 بتاريخ 2026-11-22. يحدد مواقع الملفات ومسؤولياتها وفق [المتطلبات التقنية المعتمدة](TECHNICAL_REQUIREMENTS.md)، ويغطي وحدات البداية والمراكز المشتركة. المسارات البرمجية أدناه تصميم للتنفيذ التدريجي؛ لم تُنشأ ملفات التطبيق أو تُثبت الحزم ضمن هذه المهمة.

تبقى بيانات الموظفين وسياسات الإجازات والرواتب والأدوار ونطاقات الفروع وتعارض الصلاحيات في مهام متطلباتها وتصميمها. لا تعتمد هذه الوثيقة سياسة أعمال أو جدولًا أو فهرسًا بمجرد تحديد مكان ملفه. حالة المهام والقرارات في [خطة العمل](../WORK_PLAN.md)، ومرجع البيانات في [السيكما](DATABASE_SCHEMA.md).

## الأجزاء الرئيسية

| المسار | المسؤولية | حدود الاستخدام |
| --- | --- | --- |
| client/ | تطبيق React والثيم والتجاوب وPWA وشاشات الوحدات | لا يتصل بقاعدة البيانات ولا يحمل أسرار الخادم أو ينفذ قواعد صلاحيات بديلة |
| server/ | Express وtRPC والسياق والخدمات وقواعد العمل والوصول إلى البيانات | يفرض الهوية والصلاحيات ونطاق السجلات والتحقق والتدقيق فعليًا |
| shared/ | العقود والأنواع وقواعد التحقق المشتركة وتعريفات الصلاحيات ونصوص الترجمة | لا يستورد اتصال القاعدة أو بيئة الخادم أو شيفرة واجهة React |
| database/ | تعريفات Drizzle المقسمة حسب الوحدات وملفات migrations | لا يحمل منطق الشاشات أو خدمات الأعمال؛ الاتصال والمعاملات داخل server/core/database |
| docs/ | المتطلبات والهيكل والسيكما وقواعد المراكز عند تصميمها | حالات الإنجاز والقرارات تحفظ في WORK_PLAN.md لتجنب سجلات حالة متعارضة |
| references/ | نموذج المستخدم كمرجع للفكرة والثيم | لا يدخل في بناء التطبيق أو بيانات الإنتاج |

ملفات الإعداد العامة في الجذر عند التهيئة: package.json وملف قفل الحزم وtsconfig.json وvite.config.ts وvitest.config.ts وdrizzle.config.ts وإعداد بناء الخادم باستخدام esbuild. تُثبت الإصدارات وأوامر التشغيل عند M3-01. ملف .env محلي ومستبعد من Git؛ لا تدخل قيمه في التوثيق أو ناتج بناء الواجهة.

| auth/ وpermissions/ | حالة المستخدم والجلسة وعرض التنقل وحراسة الصفحات؛ يبقى تحقق الخادم إلزاميًا |

كل وحدة واجهة تتبع النمط: pages/ للشاشات، وcomponents/ لعناصرها الخاصة، وhooks/ لتفاعل الوحدة مع الخدمات، وtests/ لاختبار سلوكها المناسب. لا تُنشأ هذه المجلدات أو الملفات فارغة مقدمًا؛ يُضاف الجزء الذي له استخدام فعلي عند بناء المهمة.

settings/numbering/ موضع شاشة إدارة السلاسل المخولة ضمن M3-03؛ لا يعني إضافة إعدادات أو وحدات أخرى. منطق الإصدار داخل الخادم وحده وفق وثيقة مركز الترقيم.

| الملف أو الجزء | المسؤولية |
| --- | --- |
| index.ts | بدء الاستماع ومعالج ترحيل التدقيق وإيقاف الموارد بأمان عند إنهاء التشغيل؛ الأحداث المعلقة محفوظة في القاعدة |
| app.ts | إعداد Express وتركيب tRPC ومعالجة حدود الطلب؛ لا يضم جميع قواعد أعمال الوحدات |
| config/env.ts | قراءة إعدادات الخادم والتحقق من وجودها دون إظهار القيم السرية |
| trpc/context.ts | سياق الطلب والهوية ومعلومات التتبع اللازمة؛ لا يثق بدور أو نطاق يرسله العميل بوصفه صلاحية مثبتة |
| trpc/procedures.ts | نقاط الدخول المحمية وربط الحارس ومعالجة الأخطاء والتدقيق المشترك بحسب سياسة كل إجراء |
| trpc/router.ts | تجميع مسارات المراكز والوحدات وتصدير نوع AppRouter؛ لا يحتوي استعلاماتها أو قواعد عملها |
| core/database/connection.ts | إنشاء اتصال أو تجمع mysql2 وربط Drizzle مرة مركزيًا؛ لا تنشئ كل وحدة تجمعًا مستقلًا |
| core/database/transaction.ts | إدارة المعاملات المشتركة وتمرير سياق المعاملة للعمليات التي يجب أن تنجح أو تفشل معًا |
| modules/organization/ | إعداد المنشأة وفروعها وأقسامها بالقدر اللازم لوحدات البداية؛ تفاصيله تحدد في متطلبات الأساس |

تهيأ في M3-01 [خادم Express](../server/app.ts) و[tRPC](../server/trpc/router.ts) و[الاتصال المركزي](../server/core/database/connection.ts) وشاشة الأساس في [App.tsx](../client/src/app/App.tsx). تقتصر الشاشة على فحص استجابة الخادم وتبديل اللغة. تتبع جداول الوحدات وملفات المعاملات مراحلها المبينة في الخطة.

## نمط ملفات كل وحدة على الخادم

```text
server/modules/employees/
  router.ts
  service.ts
  repository.ts
  validation.ts
  tests/
```

يطبق النمط نفسه على بقية الوحدات، وتُقسم الملفات إلى أجزاء أصغر عند وجود مسؤوليات فعلية تستدعي ذلك.

| الملف | ما يحتويه | ما يبقى خارج مسؤوليته |
| --- | --- | --- |
| router.ts | قراءات وإجراءات tRPC، وعقود الإدخال، وربط الحارس، واستدعاء الخدمة | SQL وقواعد حساب الرواتب أو الأرصدة |
| service.ts | قواعد العمل وحالات الإجراء والتنسيق مع الترقيم والتدقيق والمعاملات | تفاصيل العرض وفتح اتصالات مستقلة |
| repository.ts | استعلامات Drizzle وقراءة البيانات وحفظها، مع تطبيق نطاق البيانات وتمرير المعاملة | قرارات الاعتماد أو منح الصلاحيات من تلقاء نفسه |
| validation.ts | تحقق خاص بالوحدة على الخادم وتطبيق العقود المشتركة والتحققات المرتبطة بالبيانات | نسخ متضاربة من أنواع المدخلات أو الثقة بتحقق الواجهة وحده |
| tests/ | اختبارات Vitest لقواعد الوحدة وربطها بالمراكز، واختبارات قاعدة فعلية لما يعتمد ضمانه عليها | إعلان نجاح البيئة الفعلية اعتمادًا على بدائل وهمية فقط |

تستخدم validation.ts قواعد shared عندما تكون صالحة للطرفين، وتضيف تحقق الخادم المتعلق بالهوية والسجل وحالته. لا تكرر تعريف الحقل نفسه في مواضع متعددة دون سبب.

## أماكن المراكز المشتركة

| المركز | موقع الخادم | واجهته التنظيمية ومسؤوليته |
| --- | --- | --- |
| الدخول والجلسات | server/core/auth/ | التحقق من الهوية والجلسة وحمايتها؛ الآلية التفصيلية ضمن M2-05 |
| الصلاحيات | server/core/permissions/ | الحارس وقاعدة المنح والمنع وتحديد نطاق البيانات؛ القواعد التفصيلية ضمن M2-03 |
| الترقيم | server/core/numbering/ | service.ts للإصدار داخل المعاملة، repository.ts للأقفال والعدادات والإيصالات، formatter.ts للصيغة، validation.ts للتحقق، router.ts لإدارة الإعدادات فقط وtests/؛ التفاصيل في [تصميم الترقيم](NUMBERING_DESIGN.md)، ولا تعدّ الوحدات الأرقام بمعزل عنه |
| التدقيق | server/core/audit/ | تسجيل الأحداث الآمنة في audit_outbox وترحيلها إلى المركز والاستعادة والقراءة المحمية؛ التصميم في M2-05 |
| الأخطاء | server/core/errors/ | أخطاء المجال والرموز العامة وتنسيق رد آمن وسجل فني محمي |
| الاتصال والمعاملات | server/core/database/ | الموارد المشتركة للقاعدة وحدود المعاملات وتمريرها للوحدات |

تتبع المراكز التي لها إدارة بيانات نمط router وservice وrepository وvalidation وtests بحسب الحاجة الفعلية. الحارس لا يستدعي tRPC أو الشاشات لاتخاذ قرار؛ تستخدمه نقاط الدخول والخدمات. يمرر قرار النطاق الموثوق إلى استعلامات القراءة والتعديل، فلا يسمح معرف سجل صحيح بالوصول إلى بيانات خارج النطاق.

نصوص الرسائل العامة وأكوادها تشترك فيها الواجهة والخادم من shared؛ تبقى التفاصيل الفنية والسجلات الخاصة داخل الخادم. تُكتب قواعد الصلاحيات والترقيم والتدقيق التفصيلية في docs عند إنجاز مهام تصميمها، ولا تستبدلها أسماء مجلداتها.

تفصيل ملفات مركز التدقيق بعد M2-05: recorder.ts لكتابة الحدث الآمن مع معاملة الأعمال، وdispatcher.ts للحجز والترحيل وإعادة المحاولة، وreader.ts لقراءة المركز المحكومة بالصلاحية، وsanitizer.ts لاستبعاد البيانات السرية قبل التخزين. يبقى repository.ts للوصول إلى جداول المصدر والمركز، وtests/ لاختبارات التعطل والتكرار والاستعادة. لا يعيد dispatcher تنفيذ خدمات الموظفين؛ ينقل الأحداث فقط. هذه أسماء تصميمية ولم تنشأ كملفات برنامج بعد؛ السياسة في [تصميم الأمان والتدقيق](SECURITY_AND_AUDIT_DESIGN.md).

## الملفات المشتركة والترجمة

تفاصيل رموز الثيم والمكونات والتجاوب وlang وdir ومزود اتجاه Radix وتنظيم نصوص اللغتين في [تصميم الواجهة والترجمة](UI_THEME_AND_I18N_DESIGN.md). العربية لغة البداية والاسم الإنجليزي Madar معتمدان؛ الحفظ المحلي لتفضيل اللغة وآلية التنسيق مقترحان قبل التنفيذ، ولا يتطلب هذا التصميم تغيير قاعدة البيانات.

```text
shared/
  contracts/
    organization/
    employees/
    leaves/
    approvals/
    payroll/
  validation/
  permissions/
  errors/
  i18n/
    ar/
    en/
```

contracts/ لعقود الإدخال والإخراج والأنواع العامة، وvalidation/ لقواعد تحقق مشتركة فعلًا، وpermissions/ لتعريف أسماء الصلاحيات وأنواع النطاقات دون نسخة ثانية من محرك القرار، وerrors/ لرموز الأخطاء العامة الآمنة.

تُقسم ملفات الترجمة داخل كل لغة حسب common والمراكز والوحدات، مع مفاتيح متناظرة. لا تُدرج بيانات الموظفين أو القيم السرية ضمن ملفات الترجمة. يستخدم الخادم النصوص المطلوبة للمخرجات المولدة، وتستخدم الواجهة اللغة المختارة للحقول والرسائل. آلية حفظ تفضيل اللغة ومكتبة الترجمة إن احتاجت اعتمادًا إضافيًا تُحسم قبل التنفيذ.

## تعريفات القاعدة والترحيلات

تفاصيل الجداول والأنواع والعلاقات والمعاملات المقترحة في [قاموس SQL](DATABASE_SQL_DESIGN.md)، والجرد والفهارس وحالة التطبيق في [السيكما](DATABASE_SCHEMA.md)، والاستعلامات وخطة القياس في [كتالوج الأداء](DATABASE_QUERIES_AND_PERFORMANCE.md). لا تنشأ تعريفات وحدات الإجازات والموافقات والرواتب قبل متطلباتها لمجرد ظهور أسمائها في شجرة التصميم.

```text
database/
  schema/
    organization.ts
    auth.ts
    permissions.ts
    numbering.ts
    audit.ts
    employees.ts
    leaves.ts
    approvals.ts
    payroll.ts
    index.ts
  migrations/
```

هذه أسماء ملفات الوحدات المقترحة للتعريف، وليست قائمة جداول معتمدة أو ملفات جرى إنشاؤها. يُنشأ كل ملف عندما يُعتمد تصميم بياناته. index.ts يجمع التصديرات فقط؛ تبقى الجداول والعلاقات والقيود والفهارس في ملفات الوحدات. إعداد Drizzle في الجذر يحدد ملفات التعريف ومجلد الترحيلات عند التهيئة.

تُحفظ الترحيلات بترتيب تطبيقي واضح في migrations حتى لو مسّ ترحيل واحد عدة وحدات مترابطة. تُدرج خريطة الوحدة والترحيل وحالتهما في docs/DATABASE_SCHEMA.md. لا يُولد لكل وحدة سجل ترحيلات متعارض مع بقية القاعدة.

الفهارس جزء من تصميم الجدول وفق الاستعلامات المتوقعة، وتوثق أسماؤها وأعمدتها وترتيبها وأسبابها ونتائج قياسها في مرجع السيكما. لا تضيف هذه الوثيقة فهارس أو حقولًا افتراضية. الاتصال الفعلي وجرد القاعدة يسبقان أي تغيير عند M3-01.

## اتجاه الاعتماد وتدفق الطلب

```text
React screen
  -> tRPC client
  -> Express + tRPC context
  -> central identity and permission guard
  -> module router + input validation
  -> module service
  -> repository + trusted data scope + shared transaction
  -> Drizzle + mysql2 + TiDB Cloud
  -> audit outcome + safe response
```

هذا تدفق مسؤوليات؛ ترتيب كتابة التدقيق وحدود المعاملة وحالة فشلها يُحسم في تصميم العملية، ولا يعني السهم أن التدقيق خطوة اختيارية بعد نجاحها. الخدمات التي تنسق عدة وحدات تستخدم خدماتها المعتمدة وسياق المعاملة، دون استدعاء router لوحدة أخرى أو استيراد تفاصيل واجهتها.

- client يعتمد على shared وعميل tRPC، ويجوز استيراد نوع AppRouter باستخدام import type فقط؛ لا يستورد قيمة router أو اتصال القاعدة.
- server يعتمد على shared وdatabase/schema. لا تعتمد core على شاشات أو قواعد خاصة بوحدة أعمال.
- database/schema لا يستورد خدمات أو ملفات React. العلاقات بين وحداته توثق في السيكما ولا تُنشأ دوائر اعتماد مع الخدمات.
- shared لا يستورد تنفيذ client أو server. أي ملف لا يستخدمه جزء منفذ لا يُنشأ كهيكل فارغ.

استيراد نوع AppRouter فقط وفصل تنفيذ الخادم يتبع [توثيق عميل tRPC](https://trpc.io/docs/client/vanilla/setup). تركيب tRPC داخل Express يتبع [المحول الرسمي](https://trpc.io/docs/server/adapters/express). تقسيم تعريفات القاعدة إلى ملفات ينسجم مع [تنظيم Drizzle للسيكما](https://orm.drizzle.team/docs/sql-schema-declaration). هذه المراجع تؤكد نقاط الربط؛ توزيع المسؤوليات أعلاه تصميم خاص بالمشروع ضمن المتطلبات المعتمدة.

## التحقق من التصميم وخطوة التنفيذ التالية

يغطي التصميم الفصل بين الواجهة والخادم والمشترك والقاعدة والتوثيق، ونمط كل وحدة، ومواقع المراكز، والترجمات، والترحيلات والفهارس، وحدود استيراد الأسرار. تحقق هذه المهمة مراجعة تصميم ووثائق؛ اختبارات التشغيل واللغتين والصلاحيات والترقيم والأداء وPWA تُنفذ في مهامها، ولا تعد ناجحة الآن.

يُستخدم هذا التصميم لتنظيم التنفيذ عند M3-01 بعد استكمال قواعد الأساس اللازمة. أول مسار أعمال محدد للمناقشة في [متطلبات مسار الموظفين](FIRST_EMPLOYEE_FLOW.md)، وتبقى الأسئلة غير المجابة ظاهرة في تلك الوثيقة والخطة.

## الملفات المنفذة لمسار الدخول الأول — M3-02

- client/src/modules/auth/AuthScreen.tsx للنماذج، وuseAuth.ts لتنسيق حالة الجلسة والنشاط وCSRF الذاكري، وlib/trpc.ts للاتصال. app/App.tsx غلاف اللغة والتخطيط فقط.
