# استكمال الحارس المركزي والتوجيه

الحالة بتاريخ2026-11-24: نُفذ الاستكمال وفق C-131، ونُشر وطابقت النسخة ونجحت فحوص ADMIN وفق C-132 وفحوص kamal وفق C-133، ثم قبله المستخدم صراحة وفق D-071. لا إعادة لطلب القبول؛ تبقى حدود الأداء والأجهزة وبقية مراكز الأساس موثقة. كل صفحة جديدة تربط بالسجل والحارس ضمن مهمة بنائها، وأولها دفعة الترقيم C-134 دون تقديم الثيم.

## فحص kamal وقبول الحارس — C-133

أثبتت مساحة العمل kamal بدورhr، ثم حوّل /users و/permissions كلًا إلى /organization دون عناوين الإدارة أو بياناتها. ثبت التحديث والرجوع، ولم تظهر صفحة دخول أو دورة تحويل في الفحص. قرأ الفرع وقسمه دون نموذج أو أدوات إضافة/تعديل. طلبا GET users.list وpermissionOverrides.list من الجلسة نفسها في تبويب مؤقت أعادا JSON AUTH_FORBIDDEN وdata.httpStatus403 دون result؛ لم تُقرأ كلمات أو رموز جلسة ولم يرسل طلب كتابة تنظيمي.

الإنجليزية390=375/375 والعربية320=305/305، وأُعيد الحجم والعربية وأغلق التبويب المؤقت وبقيت جلسة المستخدم. قبل المستخدم الحارس والفروع والأقسام وفق D-071. فحوص التعارض وغياب الصفحات والسحب تبقى محلية في C-131؛ لا توصف هذه المتابعة بأنها فحص شامل لكل حالات الإنتاج أو قياس أداء.

## متابعة النشر — C-132

طابقت بايتات JS/CSS المنشورة بناء C-131، ونجح /health، ورفضت APIsللوحدات الثلاث دون دخول بـ401JSON/no-store. في جلسة ADMIN نجح التنقل بين الصفحات المخولة ومساحة العمل /، والروابط المباشرة والتحديث، وتعطيل إجراءي تغيير دور الحساب وتعطيله ذاتيًا وتعطيل تخصيصاته العشرة. انتهى التحقق الخلفي الظاهر عند استلام الجلسة دون بقاء شاشة انتظار. عرض390للإنجليزية375/375 وعرض320للعربية305/305 دون تجاوز عرض المستند؛ أُعيد الحجم واللغة العربية بعد التجربة. المجهول404JSON.

التحويل والمنع التفصيلي ناجحان محليًا في C-131؛ ينتظر اختبارهما على جلسة kamal المنشورة دخوله الخاص ثم يكمل المساعد وفق D-070. لا تغيير لحساباته أو صلاحياته من أجل الاختبار، ولا اختبارات آلية جديدة أو قبول ضمني في C-132. تتجاوز هذه المتابعة انتظار النشر المذكور في حدود C-131 التاريخية فقط؛ بقية حدود الأداء والأجهزة والقبول باقية.

## نطاق التنفيذ المثبت قبل البرمجة — D-069

- shared/permissions/pages.ts لسجل الصفحات ومحرك قرار نقي: registeredPages وPageId/PagePath وgetPage وgetAllowedLandingPages وresolvePageAccess. المدخل pathname وحالة جلسة checking/unavailable/anonymous/password_change/authenticated وصلاحيات فعالة موثوقة. المخرجات قرار checking/unavailable/login/password-change/workspace/render/redirect/no-access/not-found، دون طلب شبكة أو تغيير عنوان داخل المحرك.
- الصفحات الوظيفية المنفذة الحالية فقط: organization بصلاحية organization.read وأولوية10، users بصلاحية users.manage وأولوية20، permissions بصلاحية permissions.manage_overrides وأولوية30. جميع الصلاحيات المحددة مطلوبة ALL؛ لا استثناء بالاسم أو الدور. الصفحة الممنوعة تحول مباشرة لأول صفحة مؤهلة، وذات الصلاحية تبقى في موقعها.
- ضبط تفصيلي للحفاظ على المسارات الحالية: / تبقى مدخل الدخول وتغيير الكلمة ومساحة العمل الحالية ذات سياسة صريحة، وتستبعد من وجهات التحويل الوظيفية. لا تحويل تلقائي من مساحة العمل عند وجود صفحة مخولة؛ تحتوي روابط الصفحات المسموحة من السجل. غياب أي صفحة وظيفية يعرض نهاية عدم وجود صفحات في المسار المعروف الحالي، دون عنوان أو تحويل إضافي. هذا يحدد السلوك المقصود بدل تعميم صف «مدخل التطبيق» في المسودة أعلاه، ويحقق طلب التحويل من الصفحة الممنوعة دون كسر الرجوع إلى مساحة العمل.
- client/src/modules/auth لحارس الصفحة وتنسيق حادثة الرفض ودمج الجلسة الحالية؛ app/navigation للاستبدال الأمني ومحرك التنقل، وApp لتصنيف التخطيط من السجل. يبقى عرض نتيجة إعادة التعيين الذاتية المعزول ذا أولوية قبل الحارس، وتبقى مسودة الصفحة المعروفة غير المنتهية مع تعطيل الأفعال أثناء التحقق الخلفي؛ لا تفتح صفحة محمية جديدة أثناءه.
- تكامل useUsers وusePermissionOverrides وuseOrganization وشاشاتها بإبلاغ سبب الفشل ونوعه بدل تفسير كل403 كخروج. AUTH_REQUIRED يعيد المصادقة؛ رفض صفحة يعيد تحققًا واحدًا وينتهي بقرار مخول أو نهاية آمنة عند استمرار التعارض؛ رفض إجراء/نطاق داخل صفحة متاحة يعرض الرفض ويحافظ على الجلسة. لا إعادة إرسال تلقائي لعملية أو سلاسل فحص مكررة؛ اكتمال التحقق يثبت بنتيجة قراءة فعلية مقبولة، لا بمجرد رجوع refresh إذا كان مؤجلًا.
- Express يشتق مسارات غلاف HTML العامة من السجل؛ تبقى البيانات والإجراءات تحت الحارس الخادمي داخل المعاملات. لا SPA redirect لطلبات API ولا تغيير لمحرك المنح أو تخفيف الأقفال. تختبر مطابقة whitelist تنقل PWA للسجل؛ whitelist صفحة الانقطاع لا تمنح صلاحيات. لا اعتماد أو جدول أو فهرس أو ترحيل أو متغير نشر جديد مخطط.
- حالات النهاية مترجمة ar/en: عدم وجود صفحات مع تواصل الإدارة والخروج وإعادة تحقق يدوي، وتعذر التحقق أو استمرار التعارض دون بيانات أعمال أو تحويل متكرر، ومسار غير معروف404. لا صفحة إدارة أدوار جديدة أو سايدبار أو موظفون أو صلاحيات جديدة.
- الاختبارات: عقد السجل ومطابقة الصلاحيات والمسارات والمكونات وPWA، وخواص ثبات التحويل وعدم الهدف الذاتي أو الخارجي، والحالات والروابط والرجوع والسحب والفشل والرفض الذري مقابل منع الصفحة، وHTTP بلا تسريب، ومتصفح ببيانات معزولة. لا اتصال إنتاج أو تغير صلاحيات حسابات المنشأة للتجربة. قياس TiDB الحقيقي والأداء ليس منجزًا باختبارات الذاكرة.

النطاق والاستعلامات: هذا الاستكمال يستخدم auth/session ومخازن الوحدات القائمة فقط ولا يضيف شكل استعلام أو فهرس. لا ترقيم أعمال؛ التدقيق الخادمي القائم لرفض الإجراءات باقٍ، وأخطاء التوجيه النهائية تعرض رسالة منقحة ومرجعًا عند توفره دون تسجيل أسرار أو إعادة إغراق السجل. يُسلّم الجزء للنشر والتجربة والقبول المستقل بعد التحقق؛ لا يُعد قيد النطاق إعلان اكتمال.

## ما راجعناه وحدود الأدلة

في مراجعة ما قبل التنفيذ شملت المصادر server/core/permissions/guard.ts وserver/modules/auth/service.ts وclient/src/modules/auth/useAuth.ts وAuthScreen.tsx وapp/navigation.ts وserver/app.ts. كان القرار الخادمي المركزي موجودًا، وكانت فروع الواجهة تعرض رسائل منع دون وجهة بديلة. استُخدم useAuth القائم لتنظيم الجلسة والطلبات والنتائج القديمة ومهلة15ثانية؛ لا محرك تحديث جلسة موازٍ. نتائج التنفيذ والاختبار اللاحقة مفصّلة في آخر هذه الوثيقة، دون فحص إنتاج لهذه الدفعة.

مرجع المبادئ: [OWASP للصلاحيات](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) يؤكد المنع الافتراضي والتحقق من كل طلب وموقع فرض القرار والاختبارات؛ [OWASP للتحويلات](https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html) يوصي بوجهات موثوقة والتحقق من صلاحية الوصول إليها. ترتيب الشاشات والخوارزمية المقترحة أدناه تصميم مدار، وليسا وصفة مفروضة من المرجعين.

## مسؤوليات المركز

### الفرق عن إدارة الأدوار والصلاحيات الذرية

الصلاحية الذرية تمثل إجراءً مستقلًا مثل employees.read أو employees.update، والدور يجمع منحًا محددة. واجهة إدارة الأدوار والتخصيصات هي أداة المخول لضبط المنح والمنع بحسب النطاق المعتمد؛ الوضع الحالي في مدار دوران ثابتان وتخصيص مستخدم، دون تحرير منح الأدوار في الدفعة المقبولة. الحارس يقرأ القرار الفعلي من هذه السياسة ويفرضه وقت طلب الصفحة أو البيانات أو الإجراء، ويختار التوجيه عند منع دخول الصفحة وفق التصميم المقترح. لا يمنح الحارس صلاحيات من تلقائه، ولا يُكتفى بإخفاء أزرار واجهة الإدارة كحماية. هذا توضيح للمسؤوليات لا إضافة صفحة إدارة أو وحدة أو صلاحيات جديدة.

سجل صفحات مركزي مشترك يعرّف معرف الصفحة ومسارها ونوعها وسياسة الدخول والصلاحيات المطلوبة وهل تصلح وجهة بداية وترتيبها. يكون شرط تعدد الصلاحيات صريحًا، مثل ALL، دون افتراض أن امتلاك صلاحية عامة يسمح بكل صفحة. القوائم وحارس الواجهة واختيار وجهة البداية تستخدم التعريف نفسه. الصفحات العامة وصفحات الدخول/تغيير الكلمة والأنظمة النهائية لها سياسات صريحة وتستبعد من وجهات البداية الوظيفية.

محرك قرار محدد النتيجة يفصل عن تنفيذ التنقل. يعتمد حالة جلسة موثوقة ولقطة صلاحيات من الخادم ومسارًا معرّفًا. الواجهة تتحكم فيما يعرض للمستخدم، والخادم يظل صاحب قرار السماح بكل قراءة وإجراء وسجل ونطاق داخل المعاملة. إضافة صفحة للسجل لا تمنح صلاحيتها للأدوار؛ القاعدة المعتمدة والمنع الافتراضي باقيان. لا استثناء لاسم ADMIN أو رمز الدور.

لا إدراج لصفحات لم تنفذ أو تعطل تشغيلها أو لتفاصيل تتطلب معرف سجل باعتبارها وجهة بداية. لا اختيار تلقائي لصفحة إنشاء أو إجراء ذي أثر. تسجيل كل صفحة/صلاحية وربطها واختبارها يكون في مهمة بنائها وفق التعليمات19. يفشل فحص البناء عند صفحة وظيفية دون سياسة أو صلاحية مجهولة أو تعريف متعارض أو ترتيب بداية غير حاسم. لا صلاحية جديدة أو جدول أو مكتبة إضافية مقترحة لهذه المرحلة؛ التفاصيل التنفيذية واختباراتها توثق قبل البرمجة.

## جدول القرار المعتمد للتنفيذ

| الحالة | القرار |
| --- | --- |
| تحقق أولي جارٍ أو لا توجد لقطة موثوقة | انتظار محدود؛ لا تركيب لصفحة محمية جديدة |
| لا جلسة صالحة | عرض الدخول؛ لا رجوع تلقائي منه لصفحة ممنوعة |
| تغيير كلمة مؤقتة مطلوب | تغيير الكلمة والخروج فقط وفق المرحلة القائمة |
| الصفحة الحالية مخولة | عرضها والبقاء فيها؛ لا نقل دائم إلى أول صفحة |
| مدخل التطبيق / مع وجهة وظيفية متاحة | عرض مساحة العمل وروابط الصفحات المخولة؛ ليس وجهة تحويل وظيفية |
| صفحة معروفة ممنوعة | اختيار أول وجهة وظيفية مخولة من السجل، ثم تحويل أمني واحد إليها |
| لا وجهة وظيفية مخولة ومنفذة | شاشة نهائية «لا توجد صفحات متاحة لحسابك حاليًا»؛ تواصل مع مدير النظام، مع الخروج وإعادة تحقق يدوي فقط |
| فشل الشبكة أو تعذر التحقق | شاشة تعذر التحقق، دون ادعاء نفاد الصلاحيات أو نقل تلقائي بين الصفحات |
| مسار غير معروف | حالة404 آمنة ونهائية؛ لا تخمين صفحة أو تحويل مفتوح |

التحقق الخلفي لجلسة معروفة غير منتهية يحافظ على المسودة الحالية وفق السياسة القائمة ويعطل الإجراءات والتنقل؛ لا يفتح صفحة جديدة اعتمادًا على حالة غير متحققة. عند انتهاء الجلسة أو رفضها أو فشل التحقق تمسح البيانات المحمية كما هو موثق. شاشة عدم وجود صفحات تكون مقصورة على جلسة مصادقة صالحة ولا تعرض بيانات أعمال أو قوائم إدارة، ولا تدخل في قائمة الوجهات كي لا تعيد توجيه نفسها. لا خروج قسري بسبب غياب صفحات مع بقاء الجلسة صالحة.

## اختيار أول صفحة

ترتيب الصفحات المنفذة ضمن نطاق D-069:1الفروع والأقسام /organization بصلاحية organization.read؛2إدارة المستخدمين /users بصلاحية users.manage؛3تخصيص الصلاحيات /permissions بصلاحية permissions.manage_overrides. عند منع الصفحة يختار الحارس أول عنصر يحق للمستخدم من هذه الوجهات، دون اعتماد اسم دوره. يبقى المستخدم في صفحته الحالية المخولة وفي مساحة العمل /؛ لا يغير هذا الترتيب حالة نشر أي صفحة.

عند بناء الموظفين أو وحدة أخرى، يحدد موضعها ويضاف إلى السجل ضمن مهمتها؛ لا تضاف وجهة موظفين وهمية الآن. يعاد ترتيب الصفحة فقط بقرار موثق. مدخل التطبيق وصفحات الحالات التقنية ليست مرشحة للبدء، حتى لا يصبح المدخل وجهة تعيد احتساب وجهة أخرى بلا نهاية.

## منع الدوران والتحويل غير الآمن

1. احسب جميع الوجهات المؤهلة من لقطة واحدة ثم اختر الهدف مباشرة. لا تجرب صفحة بعد أخرى بتحويلات متسلسلة، ولا تستخدم دالة تستدعي نفسها حتى تجد وجهة.
2. تحقق أن الهدف مسجل ومفعل وآمن للدخول ومخول في اللقطة نفسها، وأنه ليس الصفحة المرفوضة ولا شاشة الدخول أو الحالات النهائية. يجب أن يعطي تقييم الهدف باللقطة نفسها قرار عرض؛ هذه خاصية ثبات يختبرها المحرك.
3. نفذ التحويل الأمني باستبدال العنوان في سجل المتصفح، دون إضافة الصفحة الممنوعة إلى سجل الرجوع أو إعادة تحميل التطبيق كله. طبّق تنفيذًا واحدًا للقرار نفسه، مع تجاهل استجابات تحقق قديمة وإعادة استخدام دمج الطلبات الحالي.
4. إذا خالفت استجابة الخادم لقطة الصلاحيات، اوقف العرض المتأثر وأعد التحقق مرة واحدة للحادثة، ثم أعد القرار. إن استمر التعارض، أنهِ التدفق بشاشة آمنة ورقم تتبع بدل تجربة بقية الصفحات. يتجدد القرار عند تنقل صريح أو لقطة موثوقة جديدة، ولا يفتح ذلك حلقة تحديث تلقائي.
5. لا تعامل كل403 كمنع للصفحة: رفض تعديل أو سجل خارج النطاق يبقى رفضًا للعملية. يعيد API خطأ JSON آمنًا401/403 وفق السبب، ولا يحوله إلى صفحة HTML أو رد نجاح. يحول حارس الصفحة فقط عندما تفقد صلاحية دخولها فعلًا.
6. الهدف يحسب من معرفات ومسارات داخلية مسجلة، دون ثقة في returnUrl أو next أو رابط خارجي/غير معروف يرسله المستخدم. تعالج مطابقة المسار وصيغته في موضع واحد دون تحويل النص غير الموثوق إلى تصريح وصول.
7. لا تعتمد مهلة انتظار طويلة أو عداد تحويلات وحده لمعالجة الدوران؛ الأصل قرار ثابت ونهايات لا تعيد التوجيه. لا إعادة طلب آلية مفتوحة أو مؤقتات تعيد فتح الصفحات كلما وقع خطأ.

## التحقق المطلوب قبل التسليم

### أثر الأداء — مراجعة مصدر فقط

اختيار وجهة من سجل صغير ومجموعة صلاحيات متحققة عمل محلي في الذاكرة؛ يقترح تجنب طلب تحقق مستقل لكل عنصر تنقل أو لكل مرشح تحويل، وتكرار فحص الجلسة بالتوازي أو إعادة تحميل التطبيق كله. يعاد استخدام useAuth ودمج الطلبات الحالي، ويبقى تحقق الخادم داخل طلب البيانات/الحفظ ومعاملته. لقطة الواجهة لتحديد العرض والتوجيه فقط ولا تستبدل تصريح الخادم الحالي.

مراجعة auth/repository تبين أن المسار المعتاد للمستخدم المصادق يقرأ الجلسة والمستخدم والدور والمنح والتخصيصات بخمسةSELECTs مقفلة، إضافة إلى استعلامات العمل والتدقيق والمعاملة. هذه تكلفة قائمة قد تتأثر بزمن الشبكة إلى TiDB والتنافس على صف الدور؛ لا توجد قياسات لهذه المهمة تثبت أنها ضئيلة أو تحدد مقدارها. لا تغيير للأقفال أو تخزين صلاحيات خادمية قديمة كتسريع غير مدروس.

التحقق المقترح قبل قبول الأداء: قياس قبل/بعد لزمن قرار التوجيه المحلي وفتح الصفحة وAPI، وعدد طلبات الجلسة والاستعلامات، وp95 مع10مستخدمين متزامنين على قاعدة اختبار معزولة وEXPLAIN ومراجعة الأقفال. يفصل الفتح الأول عن التنقل العادي والحفظ، ولا يعد اختبار الذاكرة أو /health قياسًا لمسار مصادق عليه. لا وعد بزمن أو انعدام أثر قبل قياس فعلي، ولا اختبار أو تحسين أداء منفذ من هذا السؤال.

### حالات الاختبار المقترحة

- اختبارات جدول القرار، والمنع الخاص على الدور، والمنح الخاص، وعدم منح القراءة من صلاحية تعديل، وعدم وجود وجهات أو تعطيل جميعها أو صلاحية مجهولة.
- خاصية: كل هدف تحويل مسموح في اللقطة نفسها ويصبح قرار عرض عند تقييمه؛ لا هدف إلى نفسه ولا دورات بين مرشحين.
- اختبارات رابط مباشر/تحديث/رجوع/تنقل داخلي وتغيير الصلاحية وانتهاء الجلسة وسحبها، والمرحلة المؤقتة، وطلبات متزامنة ونتيجة تحقق قديمة وتكرار أحداث العودة.
- فشل الاتصال503، ومخالفة الصلاحيات بعد التحويل، وتوقف إعادة التحقق بعد محاولة واحدة للحادثة، مع عدم فقد النهايات الآمنة أو عرض بيانات محمية أثناء التحقق الأولي.
- استمرار API في منع القراءة/الإجراء المباشر ونطاق السجل حتى مع إخفاء القوائم أو تزوير معلومات العميل؛403 لعملية ممنوعة لا يخرج المستخدم من صفحة عرض مسموحة.
- اختبار أن كل صفحة جديدة مسجلة وكل صلاحية معروفة وأن المنح ليست تلقائية. فحص اللغة والاتجاه والجوال ورسائل النهاية والأخطاء والتدقيق الآمن لرفض الخادم وأخطاء سلامة التوجيه دون أسرار أو إغراق متكرر.

سُجل نطاق التنفيذ وملفاته قبل البرمجة في C-130 وفق D-069. نتائج التحقق الفعلية تسجل عند تنفيذها؛ هذه القائمة وحدها لا تثبت نجاحها. يبقى رفض تقديم الثيم D-066 قائمًا؛ هذا الاستكمال لا يتطلب بناء السايدبار أو وظائف أعمال جديدة.
