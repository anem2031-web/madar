# تحقق TiDB الفعلي ضمن M3-06

بتاريخ 2026-11-25 بتوقيت الرياض، وفق D-084 وC-185. **النتيجة الإجمالية: نجحت فحوص سلامة البيانات والإعادة والتدقيق، وفشل اختبار سعة مجمع اتصال التطبيق عند عشرة طلبات. لا تُعد M3-06 مكتملة.** النتائج المقاسة محفوظة في [السجل المنقح](TIDB_TEST_RESULTS.json).

## البيئة والحدود

- قاعدة الاختبار المصرح بها `madartest`؛ أظهر الجرد الأول أنها فارغة. التحقق من `DATABASE()` إلزامي في كل برنامج اختبار، مع رفض أي اسم آخر.
- الاتصال عبر TLS مع التحقق من شهادة وهوية الخادم، بواسطة `openDatabase` وDrizzle وmysql2 المعتمدة. Node v24.15.0.
- طُبق نفس الترحيلين 0000 و0001 داخل `madartest` فقط: 41 ثم 3 أوامر DDL، دون تغيير ملفيهما أو Drizzle أو CHECK أو إعداد المثيل. أضيف سجل الترحيلين بالبصمتين والتوقيتين الأصليين، وطابق الجرد 16 جدول تطبيق و42 مفتاحًا وفهرسًا و13 علاقة.
- لم يُقرأ اتصال `.env` الإنتاجي أو تُستعمل قاعدة `madar` أو حسابات ADMIN وkamal. كلمة اتصال الاختبار في ملف بيئة محلي مستبعد من Git، دون طباعتها في السجلات أو التقرير.
- خادم HTTP الفعلي للتطبيق شُغل محليًا أثناء الفحص، واتصل بقاعدة TiDB الفعلية؛ الأزمنة تشمل شبكة جهاز التنفيذ إلى TiDB. **ليست أزمنة Railway أو جوال المستخدم، ولا SLA معتمدًا.**
- مستخدمون وجلسات وبيانات اصطناعية فقط. تهيئة الجلسات مباشرة تختبر التحقق من الجلسة والصلاحيات، ولا تدعي اختبار شاشة الدخول أو كلمة المرور أو الجوال.

| نفس عملية الإضافة عبر الخدمة والحارس والتدقيق من عشرة اتصالات | نفس الفرع للجميع؛ حدث إنشاء واحد وتسعة أحداث إعادة |
| مفاتيح مستقلة من تسعة حسابات إدارية | نجحت الإضافات التسع؛ الحساب العاشر HR اختُبر منفصلًا للمنع |

| فشل مصطنع في كتابة التدقيق داخل معاملة TiDB الفعلية | لا فرع ولا إيصال ولا حدث جزئي، ثم نجحت إعادة المحاولة |

| فحص الإيصالات بعد العمليات | لا response_json ناقص |
| عاملان فعليان لمركز التدقيق على 40 حدثًا | نقل 40 حدثًا دون تكرار، وتطابقت هوية الحدث ووقته وإجراؤه ونتيجته مع outbox |
| قراءة محدودة من 10,040 حدث تدقيق | 26 صفًا لكل قراءة؛ 30 عينة بعشرة اتصالات |

حقن الفشل فوق المستودع في تجربتي التراجع هو تحفيز اصطناعي، لكن rollback والأعمال والإيصال والتدقيق نفذت على TiDB الفعلية. لا إسقاط خدمة TiDB أو إنتاج متعمد.

## الفهرسة والقياس

استخدم EXPLAIN المفتاح PRIMARY للإيصال، و`uq_departments_branch_id(branch_id,id)` لأقسام الفرع، و`uq_employees_employee_number(employee_number_key)` للرقم، و`ix_employees_branch_number(branch_id,employee_number_key)` لقائمة موظفي الفرع مع 200 صف اصطناعي، و`ix_audit_events_actor(actor_user_id,occurred_at,event_id)` لصفحة التدقيق بترتيب تنازلي. هذه فحوص SQL وليست تنفيذ وحدة الموظفين أو قبول أدائها. أظهرت بعض الخطط `stats:pseudo`؛ لم يُشغّل ANALYZE ولم تُغير الفهارس.

## الخلل BUG-DB-01: رفض الطلبات عند امتلاء المجمع

الفحوص الأولى استعملت عشرة اتصالات مستقلة لإثبات صحة قفل الإيصال. ثم شُغل `createApp` الفعلي بمجمع اتصال واحد من `openDatabase`، كما يستعمله التطبيق، بعشرة مستخدمين وجلسات اصطناعية مستقلة:

- خمسة طلبات قائمة متزامنة: خمسة نجاحات HTTP200، بأزمنة 1011 إلى3765ms.
- عشرة طلبات: خمسة نجاحات HTTP200 وخمسة HTTP503/ORG_UNAVAILABLE. الطلبات الخمسة المرفوضة انتهت خلال23–24ms.
- الإعداد الحالي `connectionLimit: 5` و`waitForConnections: false`، ومصدر mysql2 المثبت يرفض الحصول على اتصال إضافي عند انشغال الخمسة. أكد مسبار لاحق مستقل رفض اقتراض الاتصال السادس عند حجز الخمسة، ثم نجاح الاقتراض بعد تحريرها، دون كتابة صفوف. لم يُسجل سبب mysql2 الداخلي لكل رد503 في اختبار HTTP نفسه؛ التشخيص مبني على توافق النتيجة والمصدر والمسبار. لا يُعمم ذلك إلى «كل عشرة مستخدمين يفشلون دائمًا»؛ المثبت عشرة طلبات متزامنة في هذه البيئة.

هذا إخفاق تشغيلي حقيقي في تحمل التزامن المقصود، رغم نجاح سلامة معاملات قاعدة البيانات. [مقترح الإصلاح المحدود](DB_POOL_CAPACITY_FIX_PROPOSAL.md) ينتظر موافقة النطاق؛ لم يُعدل الاتصال أو النشر أو أقفال الصلاحيات.

## التنظيف والتأجيل

نُظفت صفوف كل جولة بمعرفات مستخدميها وفروعها ومراجعها الاصطناعية، دون DROP/TRUNCATE أو حذف سجل الترحيلات. أكد الجرد الأخير صفر صف في جداول التطبيق الستة عشر، وبقي صفا الترحيل و42 مفتاحًا وفهرسًا و13 علاقة. انتهى خادم HTTP المؤقت وأغلقت الاتصالات. حُذفت ملفات التجربة وبيئتها السرية بعد حفظ التقرير، وتأكد غيابهما وإغلاق4354؛ حالة التحقق النهائي في C-186.

اختبار التثبيت والفتح على Android وiPhone **مؤجل صراحة بطلب المستخدم D-084** إلى إتاحة الأجهزة وتوجيهه، دون موعد متفق عليه. لا يُسجل كناجح أو كشرط يجب إعادته الآن. يبقى BUG-DB-01 مفتوحًا، وقياس الأداء من بيئة قريبة من خادم النشر مطلوب قبل قبول أداء الإنتاج. لا يبدأ M3-07 أو الموظفون من هذه الجولة وحدها.
