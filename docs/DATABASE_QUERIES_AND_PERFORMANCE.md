# الاستعلامات والفهارس وخطة قياس الأداء — M2-08

## الحالة ومعيار الاعتماد

أُعد بتاريخ 2026-11-22 مع [قاموس SQL المقترح](DATABASE_SQL_DESIGN.md) و[السيكما](DATABASE_SCHEMA.md). هذا كتالوج استعلامات ومبررات فهارس وخطة اختبار، وليس نتيجة EXPLAIN أو زمنًا مقاسًا. كل أشكال القوائم وحدودها وميزانيات الزمن أدناه **مقترحة للتثبيت قبل التنفيذ**؛ لا تتحول إلى متطلبات مستخدم معتمدة بالصمت.

حجم البداية المعتمد 200 موظف وفرع واحد و10 مستخدمين متزامنين. تقترح بيانات ضغط منفصلة من 2,000 موظف و10,000 حدث تدقيق و10,000 إصدار لاختبار نمو الفهارس، دون إدخالها في قاعدة المستخدم أو اعتبار ذلك حجم منشأته. لا شراء موارد أو تغيير باقات خدمات ضمن هذه المهمة.

كل قراءة محمية تخضع للصلاحية والنطاق قبل إعادة البيانات، وتكتب حدث الاستعراض بالمستوى المعتمد. لا يعني ذكر استعلام هنا وجود شاشة جديدة أو منحه لدور لا يملكه. أسماء الفهارس المعتمدة للتوثيق وترتيب أعمدتها في السيكما.

استعلامات الصفحات لا تتضمن COUNT(*) لكل طلب تلقائيًا؛ إذا احتاجت الشاشة مجموعًا، يقاس استعلامه منفصلًا. cursor مربوط بالفرز والمرشحات، ويعاد التحقق من نطاق المستخدم عند كل طلب؛ ليس cursor تصريحًا للوصول. لا يبدأ دعم فرز حر بكل الأعمدة أو تصدير أو بحث تقريبي لغوي دون متطلبات واضحة.

## لماذا هذه الفهارس ولماذا لا نفهرس كل شيء؟

المفاتيح الأساسية تضمن هوية السجلات، والفريدة تضمن قواعد الأعمال وإيصالات الإعادة. المفاتيح المركبة للربط تبدأ بمرجع الأب وتدعم التصفية المقترحة نفسها بدل فهرسين متداخلين. لا فهرس منفرد إضافي على employees.branch_id بعد المركبين المخططين، ولا فهرس مستقل للقسم دون استعلام فعلي يبحث فيه دون فرعه، ولا فهرس role_id منفرد مكرر على role_permissions بعد المفتاح المركب.

فهرس الفرع/القسم/الرقم يدعم القيد المرجعي المركب وتصفية موظفي قسم داخل فرعه. فهرس الفرع/الرقم يخدم ترتيب موظفي الفرع كله دون الفرز بالقسم، لذلك ليس استنساخًا مطابقًا للأول. مرشح الحالة وحده على 200 سجل لا يبرر فهرسًا إضافيًا دون قياس. البحث contains في الاسم لا يستفيد تلقائيًا من فهرس B-tree عادي؛ يقاس المسح الصغير أولًا، ولا تضاف خدمة بحث أو FULLTEXT من تلقاء التصميم.

فهرسا التسليم والتقاط الحجز المنتهي يخدمان شرطي وقت مختلفين، فلا يعتبر أحدهما بديلًا مضمونًا للآخر. لا تفهرس payloads JSON أو كلمات البحث الشخصية أو القيم المحجوبة. لا يفترض استخدام optimizer لفهرس بعينه إذا كانت كلفة المسح أقل؛ يقبل الاختيار المفسر الذي يحقق الميزانية ويحافظ على السلامة.

## ميزانيات مقترحة للمراجعة

الأرقام أهداف اختبار أولية، **لم يقس أي منها ولم تعتمد كاتفاق خدمة**. يقاس زمن API من وصول الطلب للخادم إلى تجهيز الرد شامل الصلاحيات وكتابة outbox، دون زمن الشبكة من جوال المستخدم؛ يقاس زمن المتصفح منفصلًا. بيئة Railway وخطة TiDB ووقت الاستيقاظ والاتصال تسجل قبل مقارنة النتائج.

| المجموعة | الهدف المقترح عند 10 مستخدمين متزامنين |
| --- | --- |
| فتح ملف/دليل موظفين من 200 سجل | p95 لا يتجاوز 1 ثانية بعد إحماء الاتصال |
| حفظ/تعديل موظف مع outbox | p95 لا يتجاوز 1.5 ثانية؛ صفر حفظ جزئي أو فقد تعديل صامت |
| إصدار رقم مع حفظ أعمال وتدقيق | p95 لا يتجاوز 2 ثانية؛ صفر تكرار، ومطابقة الإيصال للعملية |
| قراءة التدقيق ضمن فترة محددة من 10,000 حدث اختبار | p95 لا يتجاوز 1.5 ثانية، وصفحة محدودة |
| استعادة التدقيق بعد توقف العامل | لا فقد ولا ازدواج؛ تقاس سرعة التصريف وأقدم حدث معلق قبل تثبيت مهلة تشغيل مستهدفة |
| الدخول وتغيير كلمة المرور | يقاسان منفصلين بسبب كلفة scrypt، مع حدود الذاكرة والتزامن؛ لا تخفض كلفة الحماية لتحقيق أرقام قراءة الدليل |

لا تعد أخطاء رفض صحيحة حالات نجاح أداء. تسجل نسبة الأخطاء الفنية وعدد retries وانتظار الأقفال والأوقات p50 وp95 والحد الأقصى؛ لا يؤخذ متوسط سريع ليخفي طلبات عالقة. اختبار الضغط الأكبر لا يغير حجم التشغيل المعلن أو الباقة دون موافقة.

## تنفيذ القياس لاحقًا

1. تسجيل إصدارات Node وmysql2 وDrizzle وTiDB وإعدادات الاتصال والمعاملات وحجم الموارد؛ لا أسرار في التقرير. تأكيد أن قاعدة الاختبار منفصلة ولا تحتوي بيانات موظفين حقيقية.
2. إنشاء بيانات ممثلة: أسماء عربية وإنجليزية، أرقام بأصفار وحروف وحالات متعارضة، بصمات NULL متعددة، فروع وقيم تصفية متفاوتة في الاختبار فقط، وسجلات تدقيق مؤرخة وفترات ترقيم مختلفة.
3. مراجعة SHOW INDEX وSHOW CREATE TABLE وتطابقها مع السيكما، بما فيها الفهارس التي قد ينشئها FK تلقائيًا؛ لا إبقاء فهرس مكرر غير مقصود.
4. تشغيل EXPLAIN للاستعلامات ثم EXPLAIN ANALYZE لقراءات مناسبة على الاختبار؛ الأخير ينفذ الاستعلام فعليًا. لا تشغيل صيغ تعديل أو حذف تحليلية على بيانات فعلية.
5. تسجيل خطة الوصول والصفوف المقروءة والمسترجعة وترتيب الفرز، وحالة الإحصاءات، والقياسات قبل/بعد أي تغيير فهرس. لا FORCE INDEX لإخفاء خطة سيئة دون تفسير.
6. اختبار 10 اتصالات مستقلة ثم دفعة ضغط منفصلة؛ فصل إحماء الاتصال عن التشغيل البارد، والإبلاغ عن كليهما. اختبار رقم واحد/سلسلة واحدة وكذلك سلاسل متعددة، ومفتاح طلب واحد معاد بالتزامن.
7. حقن فشل بين كتابة الأعمال وoutbox، وبعد COMMIT وقبل الرد، وبعد حجز التدقيق وقبل تسليمه، وبعد إدراج النسخة وقبل التأكيد؛ التحقق من الأعداد والمحتوى والعدادات وإيصالات الإعادة.
8. اعتماد النتيجة فقط بعد توثيق الميزانية المقبولة وقياسها. إذا لم تحقق، تحدد العلة أولًا ثم يعدل الاستعلام أو الفهرس ضمن مهمة موثقة؛ لا زيادة موارد مدفوعة أو اعتماد جديد دون قاعدة ضبط النطاق.

مراجع الطريقة: [تحسين SQL في TiDB](https://docs.pingcap.com/tidb/stable/sql-tuning-best-practice/) و[خطط EXPLAIN](https://docs.pingcap.com/tidb/stable/explain-overview/). أما الاستعلامات والميزانيات أعلاه فهي مقترحات مدار، وليست أرقامًا منقولة من المراجع.
