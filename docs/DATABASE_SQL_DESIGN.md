# التصميم التفصيلي لبيانات الأساس والموظفين — M2-01

## الحالة وحدود الاعتماد

أُعد بتاريخ 2026-11-22، ويُقرأ مع [السيكما](DATABASE_SCHEMA.md) و[الاستعلامات والأداء](DATABASE_QUERIES_AND_PERFORMANCE.md) و[الصلاحيات](PERMISSIONS_POLICY.md) و[الأمان والتدقيق](SECURITY_AND_AUDIT_DESIGN.md) و[الترقيم](NUMBERING_DESIGN.md). انعكست تفاصيل SQL الفنية في تعريفات Drizzle والترحيل الأولي المحلي ضمن M3-01. طلب المستخدم تطبيق الترحيل الأولي على `madar` مباشرة. حالة التطبيق وشرطه موثقان في السيكما وخطة العمل.

يشمل الأساس المطبق سابقًا15جدولًا للتنظيم والحسابات والصلاحيات والجلسات والتدقيق والترقيم وملف الموظف. أضيف محليًا بعد موافقةD-080 تصميم جدول16 لإيصالات منع تكرار الكتابة؛ ترحيله0001 غير مطبق حتى التحقق المبين في [السيكما](DATABASE_SCHEMA.md). لا تصميم لجداول الإجازات أو الرواتب أو الموافقات قبل متطلباتها، ولا بوابة موظفين أو تكامل بصمة أو تعدد منشآت. لا حاجة إلىtenant_id أو جداول نطاقات فروع للمستخدمين في البداية؛ كلا الدورين يرى جميع الفروع وفق صلاحيات الإجراء، ولا يمنح ذلك وحدات أخرى.

### إضافة إيصالات الكتابة — D-080/C-164

write_operation_receipts مقسم في تعريفDrizzle مستقل، بأعمدةoperation_id وactor_user_id وoperation_code وinput_hash وreservation_token وresponse_json وcreated_at. جميعهاNOT NULL عداresponse_json الذي يمثل حجزًا داخل المعاملة حتى اكتمال النتيجة. PRIMARY(operation_id) هو المفتاح الفريد الوحيد؛ INDEX(actor_user_id) يدعمFK إلىusers(id) معRESTRICT للحذف والتحديث. لا فهارس بحث أوتنظيف تلقائي أوإيصالات تحتوي كلمات مرور أو رموز دخول. [قاموس الحقول والفهارس والتحقق والاستعادة](DATABASE_SCHEMA.md) هو التفصيل المتزامن مع [الترحيل الإضافي](../database/migrations/0001_write_operation_receipts.sql).

تثبت المعاملة الحجز بINSERT ON DUPLICATE KEY UPDATE مطابق للمفتاح، ثمSELECT FOR UPDATE. تميز ملكية الحجز بreservation_token لاaffectedRows؛ إكماله وإلغاؤه مقيدان بالمفتاح والرمز وresponse_json IS NULL. تحفظ الأعمال والتدقيق والنتيجة في معاملة واحدة، وتلغى حجوزات الرفض المملوكة أوتتراجع المعاملة عند العطل. الجرد الفعلي السابق15/40/12 لا يتحول إلى16/42/13 من إنشاء الملفات. لقطة0001 لم تغير أي جدول سابق، وبقيت بصمة0000 كماهي. اختباراتSQL المحاكية ليست اختبارًا لأقفالTiDB أوخططEXPLAIN الفعلية.

**القرار التنظيمي المعتمد:** يختار الموظف الفرع ثم القسم التابع له؛ تبقى تسمية «الفرع» وفق توضيح المستخدم الأخير. يرتبط كل قسم بفرعه، ولا تسمح القاعدة بربط الموظف بقسم من فرع آخر. المسمى الوظيفي نص معتمد، ولا جدول job_titles.

## قواعد الأنواع المشتركة المقترحة

| الرمز في الجداول أدناه | SQL المقترح وطريقة التعامل |
| --- | --- |
| ID | CHAR(36) CHARACTER SET ascii COLLATE ascii_bin؛ UUID من node:crypto في الخادم، لا الرقم الوظيفي أو رقم الطلب؛ لا معنى ترتيبيًا للمعرف |
| TIME | DATETIME(3)، UTC، ودقة مللي ثانية؛ تضبط جلسات mysql2 على UTC وتختبر القراءة والكتابة؛ وقت الأحداث من الخادم لا المتصفح |
| VERSION | INT UNSIGNED NOT NULL DEFAULT 1؛ نسخة فنية للتزامن، لا حالة أعمال أو تاريخ مفترض |
| KEY | مفتاح نصي معياري بمقارنة utf8mb4_bin أو ascii_bin وفق مجموعة محارفه؛ الطول يحدد لكل حقل |
| HASH | BINARY(32) لبصمة SHA-256؛ password_hash مستثنى ويستخدم نص الصيغة الكاملة |
| BOOL | BOOLEAN NOT NULL مع قيم 0 و1 والتحقق منها؛ لا افتراض أن الاسم وحده يمنع قيمة أخرى |

معظم النصوص utf8mb4، مع اختيار collation صريح للمفاتيح. لا يُستخدم collation يتجاهل اللكنات لتنفيذ شرط تجاهل حالة الحروف فقط. أنواع MySQL النصية والعددية والتاريخية وJSON موثقة في [أنواع TiDB](https://docs.pingcap.com/tidb/stable/data-type-overview/)، وتختلف المساواة باختلاف [collation](https://docs.pingcap.com/tidb/stable/character-set-and-collation/)، لذلك تختبر القيم العربية والحروف والأصفار قبل تثبيت التعريفات.

كل حقل NOT NULL ما لم يذكر NULL صراحة. وقت الإنشاء والتعديل يكتبه الخادم داخل المعاملة؛ لا قيم NOW افتراضية تخفي وقتًا مختلفًا بين سجلات العملية. لا أعمدة مالية أو أرصدة تجريبية. القوائم المحدودة وصحة القيم تتحقق في الخادم قبل كتابة البيانات ضمن مهام الوحدات. وفق D-052 يجهز الترحيل الأولي بدون CHECK، ويحتفظ بـNOT NULL والتفرد والعلاقات والأعمدة المولدة. تحقق الخادم لهذه الوحدات لم يُنفذ بعد.

## organization.ts — الفروع والأقسام

### branches

| الحقول | النوع والقواعد |
| --- | --- |
| id | ID؛ المفتاح الأساسي |
| name | VARCHAR(150)؛ اسم غير فارغ؛ لا يفرض تفرده دون متطلب |
| created_at, updated_at | TIME |
| version | VERSION |

لا يضاف عنوان أو هاتف أو سجل تجاري أو رمز فرع إلزامي لم يطلبه المستخدم. الاسم بيانات أعمال يكتبها المخول، ولا تُترجم قيمه تلقائيًا؛ ترجمة تسمية «الفرع» في الواجهة منفصلة. إعداد قوائم الفروع والأقسام اللازمة للملف ضمن الأساس والإعدادات المخولة، وقراءتها عبر organization.read. لا حذف مرجع مستخدم في موظف.

### departments

| الحقول | النوع والقواعد |
| --- | --- |
| id | ID؛ المفتاح الأساسي |
| branch_id | ID؛ إلزامي، مرجع branches؛ القسم تابع لفرع واحد |
| name | VARCHAR(150)؛ غير فارغ |
| created_at, updated_at | TIME |
| version | VERSION |

القيد UNIQUE على (branch_id, id) هدفه أن يكون الزوج مرجعًا لقيد الموظف المركب، وليس منع تكرار أسماء الأقسام. قائمة الأقسام تقرأ بالفرع المختار؛ عند تغييره يجب إعادة اختيار قسم تابع له. نقل قسم مستخدم إلى فرع آخر ليس إجراءً تلقائيًا، ولا تغير الفروع التاريخية للموظفين بسبب تعديل مرجع من دون مسار معتمد.

الحقول الأربعة عشر هي حقول العمل المعتمدة؛ المعرفات المولدة والنسخة والتواريخ أعمدة فنية لا حقول جديدة يملؤها المستخدم. لا ينقص الرقم الوظيفي أو تتحول «001» إلى «1»، ولا توحد الأرقام العربية واللاتينية أو المسافات الداخلية من تلقاء التطبيق. لا تتغير حالة حروف القيمة المعروضة عند إنشاء مفتاح المقارنة. إعدادات اللغة لا تغير طريقة التفرد.

المقترح تنفيذ مفتاح المقارنة بعمود مولد، حتى لا يستطيع مسار حفظ نسي تحديثه. تدعم TiDB فهرسة الأعمدة المولدة، ولها قيود عند تغيير بعض أنواعها؛ لذلك يراجع الترحيل وتستخدم الاستعلامات اسم المفتاح مباشرة بدل افتراض استبدال تعبير تلقائي. المرجع [الأعمدة المولدة](https://docs.pingcap.com/tidb/stable/generated-columns/). التعبير أعلاه مقترح يحتاج اختبار LOWER وTRIM وUnicode وNULL في النسخة الفعلية؛ تقص طبقة الإدخال المسافات الطرفية قبل التخزين، ولا تعتمد على قص SQL للمحارف الطرفية كلها.

قبل إدخال أرقام قائمة، تفحص الأطوال والتعارضات بعد التطبيع دون تعديل بيانات فعلية صامتًا. أي رقم قائم أطول من المقترح يمنع اعتماده حتى توسيع التصميم؛ لا قص صامت. محاولة تعديل برقم نسخة قديم ترفض برسالة تعارض وتطلب إعادة التحميل، دون مسح إدخالات المستخدم أو تحويلها إلى نجاح.

## تخزين السياسة المركزية

يحمل `permissions.ts` تعريف الأدوار والصلاحيات ومنح الأدوار. يحمل `permission-overrides.ts` تخصيصات المستخدم لأنها تربط جدول الحسابات بجدول الصلاحيات.

| الجدول | الحقول والأنواع المقترحة | المفاتيح والقواعد |
| --- | --- | --- |
| roles | id: ID؛ code: VARCHAR(64) ascii_bin؛ name: VARCHAR(150)؛ version: VERSION؛ created_at وupdated_at: TIME | PK id وUNIQUE code؛ البداية system_admin وhr وفق المنح المعتمدة |
| permissions | code: VARCHAR(96) ascii_bin | PK code؛ مفاتيح الإجراءات العشرة الحالية في السياسة، لا مفتاح عشوائي ينشئ وظيفة |
| role_permissions | role_id: ID؛ permission_code: VARCHAR(96) ascii_bin | PK مركب؛ وجود الصف منح للدور، وغيابه لا يمنح؛ مراجع للدور ومفتاح الصلاحية |
| user_permission_overrides | user_id: ID؛ permission_code: VARCHAR(96) ascii_bin؛ effect: VARCHAR(5) ascii_bin؛ updated_at: TIME | PK مركب؛ effect إما grant أو deny بما يطابق الحارس المنفذ؛ حذف التخصيص يعيد الوراثة، ولا يساوي deny |

users.role_id يحدد دور الحساب. لا جداول مجموعات أو صلاحيات لكل حقل أو تخصيص فرع لم يطلب. كل تغيير تخصيص يزيد users.auth_version، وكل تغيير منح دور يزيد roles.version. قبل الطلب المحمي تُقرأ السياسة الحالية؛ لا تحمل الجلسة نسخة من المنح تعد مصدر الحقيقة. لا تجاوز لمدير النظام، ولا يحذف التطبيق دورًا مستخدمًا في حساب. منع القفل الإداري الكامل أو حذف الحسابات سياسة لم تحسم؛ لا تضف تجاوزًا سريًا لمعالجتها.

## audit.ts — المصدر الدائم ونسخة العرض

الجدولان يحملان أعمدة الحدث الآمن نفسها أدناه؛ بيانات التسليم في outbox فقط. تنقيح المحتوى يسبق الجدولين. لا تحفظ الأرقام الشخصية الخام في before_values وafter_values.

| أعمدة الحدث | النوع والقواعد المقترحة |
| --- | --- |
| event_id | ID؛ PK في المصدر وفي النسخة؛ المعرف نفسه دون إعادة توليد |
| occurred_at | TIME؛ وقت الخادم |
| actor_user_id, actor_role_id | ID NULL؛ لقطة الهوية المتحقق منها؛ مرجع منطقي يحفظ التاريخ دون حذف متسلسل |
| actor_role_code | VARCHAR(64) ascii_bin NULL. لقطة رمز الدور وقت الحدث |
| module, action | VARCHAR(64) وVARCHAR(96) ascii_bin؛ قيم من عقد الخادم |
| entity_id | ID NULL؛ السجل التقني لا الرقم الظاهر وحده |
| entity_version | INT UNSIGNED NULL؛ نسخة مورد الأعمال التي عدلت أو قرئت |
| request_id | ID؛ ربط آمن بطلب الخادم، وليس رمز جلسة |
| result | VARCHAR(16) ascii_bin؛ success أو denied أو failed |
| reason_code | VARCHAR(96) ascii_bin NULL؛ سبب آمن لا رسالة SQL |
| before_values, after_values, metadata | JSON NULL؛ قوائم مسموحة وحد أقصى مقترح 16 KiB للحدث بعد التنقيح؛ يثبت ويختبر قبل التنفيذ |

لا يعتمد ترتيب التغييرات على وصول المعالج. تعديل الموظف يقفل الصف، ويزيد version، ويسجل entity_version الجديدة في المعاملة نفسها؛ القراءة تسجل النسخة التي جهز الخادم ردها. يعرض التاريخ التغييرات وفق النسخ، والقراءات وفق النسخة المشاهدة والوقت وevent_id لكسر التعادل. لا يدعي ذلك إثبات ترتيب زمني شامل بين موارد مختلفة أو إثبات رؤية المستخدم. موارد الإعدادات والأدوار تستعمل نسختها؛ ما لا يملك سجلًا ذا نسخة، مثل فشل دخول، يرتب بوقت الحدث ومعرفه فقط.

| أعمدة التسليم في audit_outbox فقط | النوع والقواعد المقترحة |
| --- | --- |
| delivery_state | VARCHAR(12) ascii_bin؛ pending أو leased أو delivered أو failed؛ يبدأ pending |
| next_attempt_at | TIME؛ يبدأ بوقت إدراج الحدث |
| attempt_count | INT UNSIGNED DEFAULT 0 |
| lease_token | ID NULL؛ ملكية محاولة العامل |
| lease_expires_at | TIME NULL؛ استرداد حجز انتهى |
| delivered_at | TIME NULL؛ لا يملأ قبل تثبيت النسخة |
| last_error_code | VARCHAR(96) ascii_bin NULL؛ منقح، لا stack trace أو تفاصيل اتصال |

معالج التسليم لا يمس محتوى الحدث. لا حذف تلقائي للمصدر أو المركز، ولا منع قاعدة البيانات لمالكها الكامل مزعوم. حدود حسابات التشغيل والترحيل وصلاحيات الأعمدة تتحقق في M3-01. لا FK يمحو السجل إذا تغير المستخدم أو المورد.

## المعاملات والتزامن

| العملية | حدود المعاملة المقترحة |
| --- | --- |
| إضافة موظف | تحقق صلاحية create ونطاقه والمراجع، ثم INSERT الموظف وoutbox معًا؛ الرقم يدوي، ويعالج تعارض المفتاح الفريد برسالة الحقل |
| تعديل موظف أو حالته | قفل الحساب/الدور وفق حارس الكتابة ثم الموظف، تحقق expected_version، وتحديث الحقول المسموحة وزيادة النسخة وحدث الفرق؛ الحالة خارج التعديل العام |
| تعديل حساب أو تخصيصه | قفل المنفذ وسياسة دوره ثم الحساب المستهدف، إعادة التحقق، تحديث البيانات وauth_version عند انطباقه وoutbox؛ لا تسرب hash |
| تعديل منح دور | قفل الدور، تعديل role_permissions وزيادة roles.version وoutbox؛ الطلبات التالية تعيد قراءة السياسة |
| دخول أو تغيير كلمة | تحقق كلمة مكلف خارج قفل طويل، ثم إعادة فحص نسخة الاعتماد والحالة داخل المعاملة، وإصدار/إبطال الجلسات والحدث؛ لا قبول كلمة تم تغييرها أثناء التحقق |
| خروج | إبطال الجلسة وحفظ الحدث عند توفر القاعدة؛ عطل المعالج لا يمنع الخروج، وتعذر القاعدة لا يساوي إبطالًا مؤكدًا |
| قراءة محمية | جلب البيانات ضمن النطاق والنسخة، وإدراج حدث تجهيز الرد قبل إرسال البيانات؛ إن تعذر حفظ الأثر فلا يدعى تسجيل القراءة |
| أعمال ذات رقم | المعاملة تملكها خدمة الأعمال، وتمرر الاتصال إلى الترقيم وoutbox؛ لا COMMIT داخلي مستقل للرقم |

ترتيب الأقفال المشترك للكتابة: الأدوار المعنية بمعرف مرتب، ثم الحسابات المعنية بمعرف مرتب، ثم السلسلة والعداد عند الحاجة، ثم موارد الأعمال المرتبة، ثم إدراج الإيصالات والأحداث. لمعرفة دور الحساب، تقرأ البيانات ثم تقفل وفق الترتيب وتعيد التحقق؛ إن تغيرت العلاقة قبل القفل تعاد المحاولة بعد التراجع. تغير تخصيص مستخدم يقفل صف الحساب نفسه، ومنح دور يقفل صف الدور نفسه، حتى لا تمر كتابة بموافقة قديمة بعد اكتمال سحبها. لا قفل طويل أثناء إرسال رد أو اتصال خارجي أو scrypt.

يلزم اختبار التراجع الصريح الكامل عند خطأ، ومعالجة أنواع أخطاء التعارض المحددة فقط، وعدد محاولات ومهلة معلنين قبل التنفيذ. عند COMMIT مجهول لا يعاد تشغيل أثر أعمال بلا إيصال؛ مركز الترقيم يستخدم إيصال الطلب المصمم، وبقية العمليات تعيد التحقق من النسخة/الحالة أو تعرض عدم وضوح النتيجة. مرجع تصنيف أخطاء المعاملات [دليل TiDB](https://docs.pingcap.com/tidb/stable/dev-guide-transaction-troubleshoot/). لا تدعي هذه الوثيقة تنفيذ آلية retries.

## حجز التدقيق وتسليمه واستعادته

1. يجد العامل دفعة pending مستحقة عبر فهرس التسليم. يحاول حجز كل حدث بتحديث مشروط حالته وموعده، مع lease_token جديد ومهلة؛ العامل الذي لم يؤثر تحديثه في صف لا يملك الحدث.
2. بعد الحجز، يبدأ معاملة قصيرة ويقفل صف outbox، ويتأكد من token والمهلة. يدرج audit_events بالمعرف نفسه؛ إذا وجد المعرف، يقارن محتوى الحدث الآمن. اختلافه خطأ سلامة، ولا يُخفى بـINSERT IGNORE عام.
3. يثبت إدراج النسخة وتحديث delivered_at وحالة delivered في المعاملة نفسها. يمنع token عاملًا قديمًا من تأكيد عمل عامل جديد بعد انتهاء الحجز.
4. يجلب العامل الحجوزات المنتهية باستعلام وفهرس منفصل، ويعيدها pending بتحديث مشروط قبل إعادة المحاولة. فشل مؤقت يحدد موعدًا لاحقًا؛ الدائم يبقى failed للمراجعة ولا يحذف الحدث.
5. لا اعتماد على SKIP LOCKED أو قفل نطاق غائب غير متحقق منه، ولا حاجة إلى وسيط رسائل أو خدمة جديدة. آلية الحجز تختبر باتصالين وعاملين وتوقف العملية بين كل مرحلتين.

لا تُشترط معالجة الأحداث بترتيب وصولها لإظهار تاريخ التغيير؛ الترتيب الدلالي بالنسخة محفوظ في محتواها. تغيير صيغة عرض التاريخ لا يعدل المصدر. مهلة الحجز وحجم الدفعة والتأخير تحدد بعد القياس، وليست أرقامًا مفترضة ناجحة.

## خطة الترحيل والتحقق والاستعادة

يجمع [index.ts](../database/schema/index.ts) تعريفات الجداول. ولّد Drizzle Kit [الترحيل الأولي](../database/migrations/0000_initial_foundation.sql). يسبق إنشاء الجداول والفهارس إضافة العلاقات، وتبقى السيكما مرجع الأعمدة والمبررات وحالة التحقق. الحزم والأوامر مثبتة في المستودع.

وفق D-050 إلى D-052 ينفذ المستخدم الترحيل الأولي يدويًا في قاعدة `madar` مع بقاء إعداد CHECK الحالي. يُجرد المخطط قبل التطبيق، وتُراجع صلاحيات حساب الترحيل وتفعيل العلاقات المرجعية. إذا وجدت بيانات تُراجع التعارضات بعد التطبيع وتُجهّز نسخة قابلة للاستعادة. يُقارن `SHOW CREATE TABLE` و`SHOW INDEX` مع السيكما وتُختبر العلاقات والتفرد والأعمدة المولدة، ثم تنفذ سيناريوهات التزامن والتدقيق والأداء في مهامها. طبق المستخدم الترحيل يدويًا وطوبقت بياناته الوصفية وسجل Drizzle وفق النتائج المرسلة بتاريخ 2026-11-23، والتفصيل في DATABASE_SCHEMA.md. لم تُنفذ اختبارات الإنفاذ السلوكية أو EXPLAIN بعد، وتبدأ مع بيانات التجارب والوظائف المعنية.

عند فشل ترحيل جزئي لا يفترض تراجع DDL تلقائيًا؛ يجرد ما طُبق ثم يصلح بترحيل موثق. لا DROP أو مسح بيانات حقيقية لاستعادة البداية دون موافقة صريحة. استعادة نسخة بيانات قديمة لا تبيح إعادة إصدار أرقام سُلّمت بعد تاريخها؛ يبقى الإصدار متوقفًا حتى تسوية سجل الإصدارات. نتيجة مراجعة هذه الوثيقة وتفاصيل الانتظار تسجل في الخطة، ولا تساوي قبولًا وظيفيًا.
