# المتطلبات التقنية الملزمة لمدار

هذه المتطلبات معتمدة من المستخدم بتاريخ 2026-11-22 بتوقيت الرياض، ومحدّثة وفق النص المرفق «متطلبات بناء المشروع» الذي أضاف تنظيم المشروع والملفات وأكد حفظ الأسرار في متغيرات البيئة. تُطبّق منذ تأسيس المشروع وعلى كل وحدة ومرحلة بحسب ما ينطبق عليها. نطاق البداية هو الموظفون والإجازات والموافقات والرواتب لمنشأة المستخدم وفروعها. تبقى حالة التنفيذ في [خطة العمل](../WORK_PLAN.md)، وتُقرأ [تعليمات العمل](../AGENTS.md) قبل كل مهمة.

## طبيعة التطبيق

يُبنى مدار كتطبيق ويب يعمل على الكمبيوتر والجوال، بواجهة واضحة وسهلة الاستخدام ومتجاوبة مع أحجام الشاشات المختلفة. يدعم PWA ليتمكن المستخدم من تثبيته على الشاشة الرئيسية للجوال وفتحه من أيقونة.

دعم التثبيت متطلب أساسي. يقترح تصميم M2-06 أن تعمل العمليات عبر الخادم وأن تعرض واجهة الانقطاع رسالة عامة. تخضع عمليات الحفظ والبيانات المحمية لسياسة منع التخزين الموثقة، ويُختبر التثبيت والتحديث على البيئة المستهدفة. [تصميم PWA والتشغيل](PWA_AND_DEPLOYMENT_DESIGN.md).

تُستخدم مكتبات المستندات والرموز والرسوم عند الحاجة الفعلية داخل مهمة معتمدة. ثبتت إصدارات حزم الأساس في [package.json](../package.json) و[ملف القفل](../package-lock.json). اختُبرت التهيئة المحلية على Node.js 24.15.0 وnpm 11.12.1. يخضع تغيير التقنيات أو إضافة الاعتمادات خارج الطلب لقاعدة التوسع في AGENTS.md.

يُجهّز مدار محليًا. يتولى المستخدم ربط حساباته ورفع الإصدارات إلى GitHub والنشر على Railway. نجح اختبار TiDB والجرد للقراءة باستخدام `DATABASE_URL` المحدث. تُحدد بيئة الوجهة قبل أي ترحيل. تحفظ مفاتيح الاتصال والأسرار في متغيرات البيئة خارج الكود والواجهة والمستودع والسجلات.

## تنظيم المشروع والملفات

يُنظم المشروع حسب الوحدة والوظيفة، بحيث يكون لكل وحدة مكان واضح يسهل تطويرها وصيانتها. هذا التنظيم متطلب ملزم عند تهيئة التطبيق وإضافة وحداته، وليس إعادة هيكلة تؤجل إلى نهاية البناء.

| الجزء | التنظيم المطلوب |
| --- | --- |
| الواجهة client | شاشات منظمة حسب الوحدات، ومجلد للمكونات المشتركة مثل الأزرار والجداول والنماذج |
| الخادم server | خدمات مركزية، ولكل وحدة مجلد مستقل يضم ملفاتها مقسمة حسب الوظيفة: المسارات، وقواعد العمل، وقراءة البيانات وحفظها، والتحقق من المدخلات، والاختبارات |
| الملفات المشتركة shared | أنواع البيانات وقواعد التحقق وتعريفات الصلاحيات المشتركة بين الواجهة والخادم؛ يظل فرض الصلاحيات والتحقق الفعلي من المدخلات على الخادم |
| قاعدة البيانات | تعريفات جداول Drizzle مقسمة إلى ملفات حسب الوحدات، وملفات إنشاء الجداول وتعديلها محفوظة في مجلد ترحيلات منظم باسم migrations |
| الاتصال والمعاملات | مكان مركزي للاتصال بقاعدة البيانات وإدارة المعاملات، تستخدمه عمليات الوحدات والمراكز المشتركة |
| التوثيق docs | شرح هيكل المشروع وقواعد الصلاحيات والترقيم والتدقيق وتحديثها مع تغييراتها المعتمدة |

لا تُجمع عمليات جميع الوحدات أو استعلاماتها أو تعريفات جداولها في ملف واحد كبير. تُستخدم قاعدة تنظيم واحدة عند إضافة كل وحدة جديدة، مع ربطها بالخدمات المركزية المطلوبة وتحديد صلاحياتها وترقيمها وتدقيقها واختباراتها.

تحدد [وثيقة هيكل المشروع](PROJECT_STRUCTURE.md) مسؤوليات المسارات وحدود الاعتماد. بدأت M3-01 بتنفيذ ملفات الواجهة والخادم والعناصر المشتركة اللازمة لفحص الاتصال. تضاف ملفات الوحدات والمراكز حسب مهامها ووظائفها الفعلية.

## مزامنة السيكما مع تغييرات القاعدة

المرجع المكتوب للمخطط هو [docs/DATABASE_SCHEMA.md](DATABASE_SCHEMA.md)، وتبقى تعريفات Drizzle مقسمة حسب الوحدات. عند أي إضافة أو تعديل أو حذف أو إعادة تسمية لجدول أو حقل أو علاقة أو قيد أو فهرس، يجب تحديث تعريفات Drizzle وملفات migrations وهذا المرجع فورًا ضمن التغيير نفسه، وتسجيل التنفيذ والتحقق في الخطة.

لا يُسمح بتغيير القاعدة مباشرة وترك السيكما قديمة أو تحديث التوثيق لاحقًا بعد إغلاق المهمة. يُوثّق وضع التصميم والترحيل والتطبيق الفعلي بوضوح؛ ولا يُعد التغيير مكتملًا قبل التحقق من تطابق المخطط الفعلي والتعريفات والترحيل والتوثيق. لا تُحذف الترحيلات التاريخية المطبقة للتخلص من آثار التغيير؛ تُنظف العناصر المتقادمة بترحيل مناسب وفق تعليمات سلامة البيانات.

## فهرسة قاعدة البيانات

الفهرسة متطلب ملزم منذ تصميم البيانات، وتُراجع عند كل إضافة أو تعديل لجدول أو استعلام. تُصمم الفهارس وفق طرق الوصول الفعلية للبيانات وحجمها المتوقع، وتُتحقق عند التنفيذ بدل افتراض أن وجودها وحده يثبت كفاءة الأداء.

1. مراجعة المفاتيح الأساسية وقيود التفرد التي تتطلبها قواعد العمل، ومنها عدم تكرار الأرقام الصادرة بالنطاق المعتمد لكل سلسلة.
2. تحليل استعلامات الربط والبحث والتصفية والترتيب والتقارير، بما فيها شروط الفروع ونطاقات الصلاحيات، لتحديد الفهارس المطلوبة.
3. اختيار الفهارس البسيطة أو المركبة وترتيب أعمدتها بما يناسب الاستعلام، مع مراجعة الفهارس الموجودة لتجنب التكرار.
4. عدم إنشاء فهرس لكل حقل تلقائيًا، وموازنة أثره على القراءة مع تكلفة الكتابة والتخزين. لا تُضاف فهارس بلا استخدام أو سبب موثق.
5. توثيق اسم كل فهرس والجدول وأعمدته بالترتيب ونوعه وسبب وجوده والاستعلامات المستفيدة وحالة تطبيقه في docs/DATABASE_SCHEMA.md، ومزامنته مع تعريفات Drizzle وملفات migrations فورًا.
6. مراجعة خطط التنفيذ باستخدام EXPLAIN وقياس الاستعلامات المهمة ببيانات اختبار ممثلة للحجم والتوزيع المتوقعين، وتحديد معيار الأداء قبل الحكم عليه. يُستخدم EXPLAIN ANALYZE عند الحاجة في بيئة اختبار مناسبة؛ فهو ينفذ الاستعلام فعليًا.
7. تسجيل نتائج التحقق ومراجعة الفهارس عند تغير الاستعلامات أو حذفها، وإزالة المتقادم منها بترحيل موثق بعد التحقق من الاستخدامات ذات الصلة.

تستند قواعد اختيار الفهارس وموازنة كلفتها إلى [دليل TiDB لتحسين SQL](https://docs.pingcap.com/tidb/stable/sql-tuning-best-practice/)، وطريقة التحقق من خططها إلى [دليل TiDB لخطط التنفيذ](https://docs.pingcap.com/tidb/stable/explain-overview/). توثق السيكما وقاموس SQL و[كتالوج الاستعلامات](DATABASE_QUERIES_AND_PERFORMANCE.md) مقترحات الجداول والفهارس ومسارات الوصول والميزانيات؛ لم تُنشأ فهارس فعلية أو تُقَس بعد، وتراجع ملاءمة النسخة عند التهيئة.

## العربية والإنجليزية

العربية لغة البداية المعتمدة مع حفظ اختيار المستخدم عند التبديل. اسم البرنامج بالعربية «مدار» وبالإنجليزية «Madar». وثقت M2-02 نتائج فحص المصدر ومعاينة الرابط المنشور ومقترحات التنظيم. تشمل الوثيقة 20 حالة اختبار لتطبيق مدار عند بنائه، منها اتجاه اللغتين واللمس والتجاوب. [تصميم الثيم واللغتين](UI_THEME_AND_I18N_DESIGN.md).

1. يدعم التطبيق العربية والإنجليزية من البداية، مع تغيير اللغة من داخل البرنامج.
2. تكون الواجهة RTL بالعربية وLTR بالإنجليزية. تُراعى المحاذاة واتجاه القوائم والجداول والنماذج والأسهم والأيقونات على الكمبيوتر والجوال.
3. تظهر الرسائل والتنبيهات وتسميات الحقول ورسائل التحقق والأخطاء باللغة المختارة. لا تُترك رسائل تقنية خام أو نصوص واجهة غير مترجمة في لغة أخرى.
4. تُنظم نصوص الترجمة بطريقة تسهّل تعديلها وإضافة لغات مستقبلًا. تُحدد طريقة التنظيم في التصميم قبل بناء الشاشات.
5. تُختبر الشاشات والمستندات والتقارير باللغتين، بما يشمل وضوح النصوص وصحة اتجاهها. تُتحقق مخرجات PDFKit وExcelJS فعليًا عند تنفيذها، ولا يُفترض سلامتها لمجرد نجاح إنشاء الملف.

## مركز الصلاحيات والحارس المركزي

يُبنى المركز في الأساس المشترك قبل وحدات الأعمال، ويُستخدم من جميع الوحدات.

- **الأدوار:** يُمنح المستخدم دورًا يحتوي على صلاحيات محددة.
- **تخصيص المستخدم:** يمكن منحه أو منعه من صلاحيات تفصيلية مثل الاستعراض والإضافة والتعديل والحذف والاعتماد والرفض وتنزيل المستندات.
- **الحارس المركزي:** يتحقق من الصلاحية عند فتح الصفحات وطلب البيانات وتنفيذ الإجراءات. توحّد طريقة استدعائه بدل كتابة قواعد متعارضة داخل كل وحدة.
- **الإدراج أثناء البناء:** كل صفحة أو صلاحية جديدة تُسجل وتُربط بالمركز ضمن مهمة بنائها نفسها وفق D-068، بسياسة دخول وصلاحيات وترتيب توجيه صريح. تستند حراسة الصفحة والتنقل والتحويل إلى التعريفات المركزية، وتُحفظ حماية البيانات والإجراءات على الخادم. الربط واختباره شرط اكتمال الجزء، وتسجيل الصلاحية لا يمنحها تلقائيًا للأدوار أو المستخدمين.
- **التحقق على الخادم:** تخضع إجراءات وقراءات tRPC للتحقق الفعلي من الهوية والصلاحية ونطاق البيانات. ينطبق التحقق كذلك على أي مسار خادم منفصل، مثل تقديم ملف للتنزيل، إن وُجد. إخفاء الأزرار والقوائم لا يحقق الحماية بمفرده.
- **نطاق البيانات:** تُحدد حدود كل وظيفة، مثل بيانات المستخدم نفسه أو فريقه أو الفروع المصرح بها. لا يكفي امتلاك صلاحية الاستعراض للوصول إلى كل السجلات.
- **تعارض المنح والمنع:** القاعدة المعتمدة هي أولوية منع المستخدم على منح الدور، وإتاحة منح المستخدم لما لا يمنحه الدور، ثم الرجوع لمنح الدور عند غياب التخصيص، والمنع عند غياب المنح. لا تجاوز تلقائي لمدير النظام. المصفوفة وحالات الاختبار ونقاط الحارس في [سياسة الصلاحيات](PERMISSIONS_POLICY.md).
- **الاختبارات:** تشمل المستخدم المخوّل وغير المخوّل، وفتح الرابط مباشرة، وطلب البيانات مباشرة، وتنفيذ الإجراء، ومحاولة الوصول إلى سجل خارج النطاق المسموح.

يُحدد لكل وحدة قبل بنائها جدول الصلاحيات والإجراءات ونطاقات البيانات التي تحتاجها. مركز الصلاحيات وإعداداته يخضعان بدورهما للتحقق والتدقيق.

## مركز الترقيم الآلي

المركز الموحد مسؤول عن إصدار الأرقام التسلسلية في وحدات البرنامج التي تحتاجها، مع إمكانية إضافة سلاسل جديدة مستقبلًا. ذكر الطلبات والمستندات والبلاغات والأصناف أمثلة لأنواع السلاسل، وليس طلبًا لبناء وحدات جديدة خارج نطاق البداية.

1. تعريف سلسلة مستقلة وصيغة مناسبة لكل نوع، مثل `PR-2026-000001`؛ المثال لا يعتمد تلقائيًا كصيغة لجميع الطلبات.
2. إصدار الرقم تلقائيًا عند إنشاء السجل عبر المركز، دون عدادات مستقلة متفرقة في الوحدات.
3. منع تكرار الرقم حتى مع الإنشاء المتزامن من عدة مستخدمين. تُوثّق آلية الضمان في قاعدة البيانات وتُختبر مع اتصال حقيقي بها؛ لا يكفي اختبار ذاكرة محلية أو واجهة واحدة.
4. الافتراضي المعتمد بدء من 1 كل سنة ميلادية مع إظهار السنة، مع إمكان استمرار العداد بسياسة مستقلة لكل نوع. يثبت مرجع التوقيت قبل التنفيذ.
5. عدم إعادة استخدام رقم صدر سابقًا بعد حذف سجله أو إلغائه. تُحدد أيضًا معاملة إصدار الرقم عند فشل إنشاء السجل حتى لا يناقض هذا الشرط.
6. قصر تعديل إعدادات السلاسل على المخولين وتسجيل التغييرات في مركز التدقيق. تشمل مراجعة الإعدادات أثر تغيير الصيغة أو إعادة البدء على عدم التكرار.
7. إتاحة إضافة سلاسل واستخدامها من الوحدات اللاحقة عبر المركز نفسه.

الرقم الصادر من المركز فريد بين جميع سلاسله مع بادئة مميزة لكل نوع. أرقام الموظفين الحالية محفوظة وأرقام الجدد يدوية مع منع التكرار؛ لا تفرض عليها صيغة المركز. متطلب عدم إعادة الاستخدام لا يعني اشتراط تسلسل بلا فجوات؛ لم يطلب المستخدم هذا الشرط.

يوثق [تصميم الترقيم](NUMBERING_DESIGN.md) الإصدار بمعاملة واحدة مع الأعمال والتدقيق وإيصالات إعادة الطلب. اعتمد D-072 وD-073 بادئة نوع مستند ثلاثية على شكل Fsw وحشو4خانات وسنة الرياض وتثبيت إعدادات الرقم بعد أول إصدار مع إتاحة التعطيل؛ يبقى سجل الرقم بعد حذف/إلغاء المستند ولا يعاد استخدامه. أول دفعة M3-03 لإدارة السلاسل في NUMBERING_SETTINGS.md، ولا يعني بناؤها اكتمال محرك الإصدار أو نجاح التزامن الفعلي.

## مركز التدقيق الشامل

يسجل المركز حركات المستخدمين بحسب طبيعتها: تسجيل الدخول، والاستعراض، والإضافة، والتعديل، والحذف، والاعتماد، والرفض، والطباعة، وتنزيل المستندات، وتغيير الصلاحيات والإعدادات. تستخدمه وحدات البرنامج من البداية.

| حقل الحركة | المطلوب |
| --- | --- |
| المنفذ | المستخدم ودوره وقت الإجراء؛ تُسجل محاولات الدخول الفاشلة بما يتوفر من هوية دون اختراع مستخدم معلوم |
| الزمن | تاريخ ووقت الإجراء وفق سياسة توقيت موثقة |
| السياق | نوع الإجراء والوحدة المتعلقة به |
| السجل المتأثر | رقم السجل أو مرجعه عندما يوجد |
| أثر التعديل | القيم قبل التعديل وبعده عند الحاجة، بعد استبعاد الأسرار والبيانات السرية |
| النتيجة | النجاح أو الرفض أو الفشل، مع السبب عند وجوده |

يحمي التطبيق سجل التدقيق من التعديل أو الحذف غير المصرح به، ويقصر البحث والتصفية والاطلاع على المخولين. لا تُسجل كلمات المرور أو رموز الدخول أو الأسرار أو البيانات السرية في القيم أو أسباب الفشل أو المرفقات الفنية.

يُحدد مستوى تسجيل الاستعراض لكل وظيفة قبل بنائها، حتى يكون السجل مفيدًا وواضحًا. يُوثق كذلك ما يمثله حدث الطباعة أو التنزيل ونتيجته الفعلية، فلا يُسجل اكتمال إجراء لم يُتحقق منه. تُحسم طريقة التعامل مع فشل كتابة التدقيق قبل بناء العمليات التي تعتمد عليه.

سجل التدقيق وسجل إصدار الأرقام سجلات وظيفية مطلوبة للحفاظ على الأثر وعدم إعادة استخدام الأرقام؛ لا تُعد بقايا كود تُحذف عند تنظيف المشروع.

حُسمت سياسة البداية: audit.read لمدير النظام افتراضيًا، ولا تعديل أو حذف عبر التطبيق أو محو آلي حتى تعتمد سياسة الحفظ. الاستعراض حدث لكل طلب قائمة أو بحث أو فتح ملف، دون تسجيل كل صف. عند تعطل مركز التدقيق يستمر العمل بحفظ الأحداث في audit_outbox داخل القاعدة ثم ترحيلها لاحقًا إلى audit_events دون تكرار أو إعادة تنفيذ الأعمال. يوضح [تصميم الدخول والتدقيق](SECURITY_AND_AUDIT_DESIGN.md) شروط الحفظ والمعاملات والاستعادة واختبار الفشل؛ لم تُنفذ هذه الآلية بعد.

## الرسائل ومعالجة الأخطاء

يعرض التطبيق رسائل مفهومة باللغة المختارة تشرح المشكلة والإجراء المطلوب، دون عرض أخطاء برمجية أو استعلامات قاعدة البيانات أو تفاصيل الاتصال.

مثال الرسالة العربية: «تعذر حفظ الطلب. يرجى التأكد من تعبئة الحقول المطلوبة.» تُستخدم عندما يطابق السبب مشكلة الحقول، وتكتب رسائل ملائمة للأسباب الأخرى مثل عدم الصلاحية أو تعذر الاتصال.

تحفظ التفاصيل الفنية اللازمة للتشخيص في سجل محمي مع استبعاد الأسرار. يمكن إظهار رقم مرجعي للمستخدم لتتبع المشكلة. تُوحّد معالجة الأخطاء عند حدود الخادم والواجهة، وتُختبر حالات التحقق والمنع والفشل الفني دون تسريب التفاصيل.

## الأمان من البداية

يشمل التصميم والتنفيذ حماية تسجيل الدخول والجلسات وكلمات المرور والملفات، والتحقق من المدخلات على الخادم، وحفظ مفاتيح الاتصال والأسرار في متغيرات البيئة خارج الكود. ينطبق ذلك على جميع الوحدات والمراكز، وعلى التنزيل والطباعة والتصدير عند إضافتها.

تُوثق آليات الدخول والجلسات والوصول للملفات قبل تنفيذها. تُراجع صلاحيات البيانات الحساسة مثل الرواتب ونطاق البيانات، وسياسة التخزين والتحديث في PWA، ضمن تصميم الأساس. لا تُستخدم بيانات الاستعراض أو تخزين المتصفح في النموذج كبديل عن هذه الآليات.

اعتُمد دخول باسم مستخدم وكلمة مرور وحسابات ينشئها مدير النظام مع تغيير الكلمة المؤقتة عند أول دخول؛ والجلسات 30 دقيقة خمول و8 ساعات مطلقة. صُممت جلسات على الخادم وCookie محمية وكلمات مرور scrypt ضمن Node.js، وحماية CSRF والأسرار والردود الفنية المنقحة في وثيقة التصميم. التنفيذ والقياس على البيئة المستهدفة يبقيان قبل التسليم الوظيفي.

## قرارات التصميم المتبقية

التقنيات وتصميم الهيكل والصلاحيات والدخول والجلسات والتدقيق والأخطاء والترقيم موثقة. وُثقت مقترحات SQL وسلامة المعاملات والقياس، وتصميم الثيم واللغتين وPWA والتشغيل. تبقى مراجعة المقترحات قبل تنفيذها، وتحديد إصدارات الحزم والموارد، وتثبيت تفاصيل الترقيم والتنسيق، وتأكيد وجهتي GitHub وRailway والتحقق الفعلي من TiDB بعد تجهيز الاعتماد. تراجع مدة حفظ التدقيق والأرشفة قبل إضافة أي محو آلي. تحدد صلاحيات الوحدات التالية مع متطلباتها.

تنفيذ دفعة مركز التدقيق M3-04 موثق في [مركز التدقيق](AUDIT_CENTER.md) وC-142 بالخطة: التحقق المركزي قبل حفظ المصدر، والنقل بمعاملات وحجز مؤقت، والقراءة المحمية والترجمة والتجاوب وحالة التسليم، دون DDL أو اعتمادات أو متغيرات جديدة. الفحوص المحلية ناجحة بحدودها؛ لا تساوي نشرًا أو قبولًا أو قياس أداء وتزامن فعليين.

نفذ M3-05 وراجع مع M3-04 محليًا وفق D-076 وC-144، بعقد أخطاء آمن ومرجع موحد وسجل فني محدود وترجمات وRTL/LTR وحاجز مراجعة للكتابة غير المحسومة. التفاصيل في [معالجة الأخطاء](ERROR_HANDLING.md). لا اعتماد أو متغير أو صفحة أو قاعدة جديدة؛ نجاح الفحوص المحلية لا يعني قبول المستخدم أو نشرًا أو تحقق أداء وتزامن البيئة الفعلية.
