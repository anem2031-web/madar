# تصميم تثبيت مدار وتشغيله — M2-06

وثيقة تصميم بتاريخ 2026-11-22. يعتمد مدار GitHub للمصدر، وRailway لتشغيل التطبيق، وTiDB Cloud للبيانات. التثبيت على شاشة الجوال ودعم العربية والإنجليزية متطلبات معتمدة. مسارات الملفات ونقاط التشغيل وسياسة التخزين أدناه تصميم مقترح للتنفيذ ضمن التقنيات المعتمدة. حالة الإعداد والاختبارات في [خطة العمل](../WORK_PLAN.md).

## التثبيت والفتح

- يقترح تقديم `/manifest.webmanifest` من أصل التطبيق عبر HTTPS. يتضمن هوية ثابتة `id` و`start_url` و`scope` بالقيمة `/` لهذا التخطيط، و`display: standalone`، واسم «مدار» وأيقونات PNG عامة بمقاسي 192×192 و512×512، مع نسخة ملائمة للقص التلقائي على الأجهزة وأيقونة Apple عند الحاجة. تفتح `/` المسار المناسب بعد تحقق الجلسة على الخادم. تثبت أسماء ملفات الأيقونات وألوانها قبل التنفيذ. معيار التثبيت ومسار البدء موثقان في [دليل تثبيت PWA](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable).
- الاسم داخل الواجهة «مدار» و`Madar` بحسب اللغة المعتمدة. الاسم الموحد تحت أيقونة الجهاز «مدار» مقترح للتثبيت الأول. تحديث اسم الأيقونة يتبع المتصفح والنظام، ولا يعتمد تبديل ترجمة الواجهة عليه.
- الاختبار على Chrome في Android وSafari في iPhone بأجهزة فعلية، مع التحقق من الأيقونة والفتح والدخول. على Android يستخدم عرض التثبيت عند توفره أو أمر المتصفح. على iPhone يُستخدم «إضافة إلى الشاشة الرئيسية» و«فتح كتطبيق ويب» حين يظهر في إصدار النظام. عند غياب التثبيت تبقى الواجهة المتجاوبة متاحة في المتصفح. [دليل Apple للتثبيت](https://support.apple.com/guide/iphone/open-as-web-app-iphea86e5236/ios).
- يضم `client/public/` ملف البيان والأيقونات العامة، و`client/src/pwa/` تسجيل عامل الخدمة وعرض حالة التحديث. يتولى البناء إصدار `/sw.js` مع رقم نسخة موارد واضح. تستدعى المكونات ورسائلها عبر طبقة الترجمة المشتركة وفق [تصميم الثيم واللغتين](UI_THEME_AND_I18N_DESIGN.md). يوفر Express المسارات الصحيحة وملفات الإنتاج.

## سياسة التخزين والاتصال المقترحة

يُقترح إبقاء عمليات مدار متصلة بالخادم في الإصدار الأول. عند انقطاع الإنترنت يمكن عرض رسالة عامة بالعربية والإنجليزية من صفحة انقطاع ثابتة، بعد اكتمال تسجيل النسخة وتخزين الصفحة. هذا التصميم يستخدم Cache Storage فقط لحزمة الانقطاع العامة المدرجة بمسارات صريحة. بقية أصول الواجهة تستخدم سياسة HTTP المعتادة أدناه.

| نوع الطلب أو البيانات | السلوك المقترح |
| --- | --- |
| صفحة الانقطاع العامة | محتوى ثابت بلا بيانات حساب أو جهة، على أصل مدار. يخزنها العامل عند تثبيت نسخته بعد نجاح تحميلها. تُستخدم للتنقل العادي في مسارات واجهة التطبيق عند فشل الشبكة فقط. يحافظ التطبيق على ردود الخادم الفعلية مثل 401 و403 و503 |
| تنقل الواجهة والروابط العميقة | من الشبكة أولًا. غلاف الواجهة العام فقط يعاد التحقق منه قبل استخدام النسخة المخزنة في HTTP، وأي صفحة مخصصة لجلسة تحمل `Cache-Control: no-store` |
| `sw.js` وبيان التثبيت | من الأصل مع إعادة التحقق قبل إعادة الاستخدام. استجابة JavaScript صحيحة للعامل وبيان صالح للمتصفح |
| CSS وJavaScript وأصول الواجهة العامة المرقمة ببصمة | يسمح لمتصفح HTTP بتخزينها مع `immutable` لأن تغيير المحتوى يغيّر اسم الملف. تغطي آلية النشر الأصول التي تطلبها الصفحات المفتوحة من النسخة السابقة قبل تنظيفها |
| tRPC والمصادقة والبيانات والتقارير والتنزيلات | من الشبكة مباشرة مع `Cache-Control: no-store` للردود المحمية. تتجاوز مساراتها عامل الخدمة بلا تحويل إلى غلاف React أو صفحة الانقطاع |
| الطلبات التي تحفظ أو تعدل بيانات | تحقق صلاحيات وجلسة وتدقيق على الخادم. إذا انقطع الاتصال بعد الإرسال يُعرض أن النتيجة غير محسومة ويُتحقق منها بعد عودة الاتصال قبل إعادة الطلب. تظل العمليات مرهونة باتصال المستخدم وقواعد الوحدة، بلا طابور كتابة محلي أو إرسال تلقائي |

عامل الخدمة يعالج طلبات التنقل من نوع GET داخل أصل التطبيق وفق قواعد المسارات. تصنف نقاط API والملفات المحمية قبل fallback الواجهة في الخادم والعامل. اختبار الخصوصية يشمل ذاكرة استعلامات الواجهة، والتنقل للخلف بعد تسجيل الخروج، والتبديل بين حسابين على الجهاز نفسه. تُمسح ذاكرة بيانات الحساب عند الخروج أو انتهاء الجلسة ويعاد التحقق قبل استرجاع الشاشة المحمية. تحفظ الجلسة في Cookie وفق التصميم المعتمد. يمكن حفظ تفضيل اللغة العام فقط وفق آليته المقترحة. [تصميم الدخول والجلسات والتدقيق](SECURITY_AND_AUDIT_DESIGN.md).

## تحديث النسخة أثناء العمل

يسجل التطبيق العامل من مسار ثابت. تحضّر النسخة الجديدة صفحة انقطاعها قبل الانتقال إلى حالة الانتظار. تعرض الواجهة إشعار تحديث عند الجاهزية. يُؤجّل التحديث أثناء حفظ جارٍ أو وجود تعديلات غير محفوظة، بما يشمل التبويبات المفتوحة التي تتحكم بها النسخة. عند تعذر التحقق من حالة التبويبات، ينتظر العامل انتهاء استخدام النسخة القديمة. بعد مراجعة الحالة، يختار المستخدم «تحديث الآن» ويتحقق التطبيق من انتقال التحكم قبل إعادة تحميل واحدة. تُنظف مخابئ مدار القديمة بحسب نسخها بعد التفعيل، وتُختبر مشكلة فقد ملف قديم عندما يبقى تبويب مفتوحًا. عند فشل تحميل الإصدار الجديد يبقى العامل السليم قائمًا ويعاد فحص التحديث لاحقًا. [دورة حياة عامل الخدمة](https://developer.chrome.com/docs/workbox/service-worker-lifecycle).

## بيئات التشغيل ومسار النشر

يتولى المستخدم رفع الإصدارات إلى GitHub وربط المستودع بـRailway ونشر نسخ التجربة والإنتاج. يجهّز المساعد النسخة محليًا ويختبرها، ثم يفحص رابط التشغيل الذي يشاركه المستخدم في مرحلة التسليم.

| البيئة | الاستخدام والحدود |
| --- | --- |
| تطوير محلي | Vite وExpress ضمن مسار التطوير المقترح. يحاكي تكامل الطلبات الأصل الواحد. يختبر العامل مع حزمة إنتاج عند تشغيلها محليًا. بيانات اصطناعية وإعدادات خاصة بالتطوير |
| اختبار وتسليم مرحلي | يقترح أصل HTTPS مستقل في Railway وقاعدة TiDB معزولة وصلاحيات خاصة بالاختبار. يستخدم للتحقق والتجربة المرحلية في M3-07 عند اكتمال الأساس. تحفظ ملفات البيئة والجلسات ومخابئ المتصفح لكل أصل منفصل |
| إنتاج | أصل HTTPS معتمد وخدمة Railway وقاعدة TiDB Cloud وبيانات اعتماد إنتاج. يبدأ التشغيل الفعلي في M7-03 بعد اختبارات الوحدات وبوابة التحقق من الاستعادة، وفق الخطة |

يُقترح مستودع GitHub خاص وخدمة Railway واحدة تقدم React المبني بـVite وواجهة tRPC من Express على نفس الأصل، مع عامل التدقيق المنصوص عليه في تصميم الأساس. يبني esbuild الخادم، ويستخدم كل تشغيل نسخة Node مثبتة وحزمًا من ملف القفل. يوثق اسم المشروع ومعرف التزام Git ورقم نسخة العامل في سجل النشر. يبدأ الخادم على `0.0.0.0` ومنفذ `PORT` المقدم من Railway. تُقصر الثقة في عناوين التوجيه على الوكيل المتحقق منه، وتستبعد مسارات API من fallback الخاص بـReact. [شبكات Railway العامة](https://docs.railway.com/networking/public-networking) و[تهيئة متغيرات Railway](https://docs.railway.com/variables).

تقترح نقطة جاهزية `/health` ترجع حالة عامة `200` عند جاهزية الإعداد والخادم والاتصال المحدود بمهلة بقاعدة البيئة الصحيحة، و`503` عند عدم الجاهزية. يُتحقق من وصول فحص Railway إليها عند تقييد المضيف، وتبقى الردود بلا تفاصيل مخطط أو اتصال. فحص Railway المدمج بوابة عند بدء النشر، ويُجرى فحص تشغيلي مستقل بعد النشر للتأكد من فتح التطبيق والدخول والبيانات. [توثيق فحص صحة Railway](https://docs.railway.com/deployments/healthchecks).

### TiDB Cloud والأسرار

1. يُؤكد نوع خدمة TiDB والمنطقة والبيئة المقصودة قبل الاتصال. يراجع مسار الشبكة بين Railway وTiDB من كل بيئة، وتستخدم آلية الوصول الموافقة لخطة الخدمة. إذا اشترطت القاعدة قائمة لعناوين المصدر، تُتحقق عناوين الخروج المتاحة في Railway أولًا. تعتمد أي كلفة أو تغيير استضافة على قرار المستخدم. [اتصال TiDB باستخدام mysql2](https://docs.pingcap.com/tidb/dev/dev-guide-sample-application-nodejs-mysql2/) و[عناوين خروج Railway الثابتة](https://docs.railway.com/networking/static-outbound-ips).
2. يُمرر `DATABASE_URL` وبيانات الجلسات إلى الخادم عبر متغيرات البيئة، بنطاق البيئة المقصودة. تظهر الأسماء وحدها في ملفات الأمثلة. تحقّق `mysql2` شهادة الطرف واسم المضيف عبر TLS وإعدادات الثقة المناسبة للخدمة. يُرفض الاتصال عند فشل التحقق. تستخدم خدمة التشغيل حسابًا محدود الصلاحيات، وتُسند الترحيلات إلى حساب مخصص. تحدد أذونات التدقيق تبعًا لتصميم الكتابة والسجل الاحتياطي.
3. بيانات الاتصال السابقة قُدمت في المحادثة. قبل أي استخدام لبيئة فعلية، على مالك القاعدة تدويرها وتعيين بيانات اعتماد بيئية بصلاحية مناسبة عبر إعدادات الأسرار. يُتحقق في M3-01 من قاعدة الوجهة والصلاحيات واتصال TLS قبل أي ترحيل. تبدأ أعمال الواجهة وهيكل المشروع المحلية مستقلة عن هذا الشرط، وتبقى أعمال الاتصال الفعلي مرتبطة بتحققه.
4. يراجع تجمع اتصالات مركزي بمهل وحدود حسب موارد البيئة، ويؤخذ مجموع اتصالات نسخ التطبيق وعامل التدقيق في الحسبان. تقاس الاستجابة ببيانات اختبار وحجم البداية المعتمد، وتُسجل القياسات عند التنفيذ في [خطة الاستعلامات والأداء](DATABASE_QUERIES_AND_PERFORMANCE.md).

### مراجعة الإصدار والترحيل والاستعادة

يبنى الإصدار من التزام معلوم بعد مراجعة الشيفرة والتحقق من الاختبارات وفحص النوع والبناء. يقترح نشر التزام التحقق في بيئة الاختبار أولًا، وتحديد طريقة السماح بنشر الإنتاج عند التجهيز. ينفذ الترحيل المراجع مرة واحدة عبر إجراء إصدار مستقل عن تشغيل النسخ اليومية. توثق نتيجة الترحيل والتحقق في السيكما والخطة، ويشترط توافقه مع الإصدار السابق إذا ظلت نسخته تخدم طلبات أثناء الانتقال. [مسار GitHub في Railway](https://docs.railway.com/deployments/github-autodeploys) و[تصميم SQL والترحيلات](DATABASE_SQL_DESIGN.md).

عند فشل جاهزية الإصدار المرشح تُراجع السجلات المحمية ومعرف الإصدار. عند اكتشاف عطل بعد التفعيل يُراجع توافق مخطط القاعدة ومتغيرات البيئة قبل الرجوع إلى إصدار التطبيق السابق. الرجوع إلى إصدار Railway يعالج الخدمة وتكوين النشر بحسب ما يدعمه الإجراء. استعادة بيانات TiDB عملية مستقلة، ويسبقها التحقق من نقطة الاستعادة واختبار نسخة معزولة وطريقة معالجة حركات التدقيق وأرقام الأعمال اللاحقة. يراجع توفر النسخ والاستعادة وفترة الاحتفاظ حسب خطة TiDB الفعلية في M7-02. [إجراءات نشر Railway](https://docs.railway.com/deployments/deployment-actions) و[مثال رسمي للنسخ والاستعادة في TiDB Cloud Starter وEssential](https://docs.pingcap.com/tidbcloud/backup-and-restore-serverless/).

## تنفيذ منطبق على مسار الدخول الأول — M3-02

أضيف client/public/manifest.webmanifest وهوية مدار وأيقونتا PNG192/512، وصفحة offline.html عامة باللغتين، وعامل sw.js لا يعترض API أو الكتابة أو الموارد أو المسارات المجهولة. يخزن صفحة الانقطاع فقط، ويعيد أخطاء HTTP الفعلية كما هي. لا skipWaiting أو انتقال قسري أثناء نماذج الدخول؛ تنتظر النسخة الجديدة إغلاق التبويبات القديمة. تسجيل العامل في بناء الإنتاج فقط.

اجتازت قواعد العامل اختبارات محلية، ونجح smoke لملفات البناء وأنواع المحتوى. فُحصت واجهة الدخول باللغتين في المتصفح بعرض ضيق على سطح المكتب؛ لا ادعاء لتثبيت فعلي على Android/iPhone أو اختبار اللمس. أسماء APP_ORIGIN وAUTH_SECRET وMADAR_ADMIN_PASSWORD موثقة في مثال البيئة، وسر التهيئة الأخيرة لا يُنشر مع بيئة التشغيل اليومية. توثيق التفعيل في README.md ونتائج التحقق والانتظار في WORK_PLAN.md. نشر GitHub وRailway يبقى للمستخدم.

مسار /users الجديد مضاف صراحة إلى تنقلات الواجهة التي يجوز عرض صفحة الانقطاع العامة لها عند فشل الشبكة؛ لا إضافة لردود API أو بيانات حساب إلى Cache Storage. اختبر العامل ذلك محليًا. تبقى متغيرات Railway كما هي عند نشر دفعة إدارة المستخدمين، ولا أوامر ترحيل أو bootstrap جديدة. بعد رفع المستخدم للتحديث يُختبر /users والدخول والصلاحيات على رابط التسليم.

أضيف /permissions إلى الغلاف العام وتنقلات العامل ضمن C-118. نجح اختبار المسار والصفحة العامة للانقطاع محليًا، وبقيت ردود API والبيانات المحمية خارج Cache Storage. البناء المحلي الجديد للعميل index-CwgPjrLK.js؛ لم يُنشر أو يُطابق مع Railway بعد، ويتولى المستخدم نشره دون متغيرات أو SQL جديدة. تجربة الجهاز والتثبيت والتحديث بين نسخ فعلية تبقى في بوابتها، ولا يثبتها اختبار العامل المحلي أو نافذة الجوال الضيقة.
